## 1. 디커플링(Decoupling)이란

**디커플링(Decoupling)**은 서로 직접 연결된 서버(시스템) 사이에 중간 전달 역할을 해주는 AWS 서비스의 활용 방식이다. 쉽게 말하면 서버와 서버를 바로 연결하지 않고, 그 사이에 택배 보관소 같은 시스템을 하나 두는 구조다.

- 기존 방식: `A 서버 ---> B 서버`
- 디커플링 방식: `A 서버 ---> 중간 서비스 ---> B 서버` (이 중간에 있는 서비스가 디커플링 서비스다.)

직접 연결 구조에서는 여러 문제가 발생할 수 있다. 예를 들어 주문 서버가 결제 서버를 직접 호출하는 구조라면, 결제 서버가 잠깐 멈추면 주문도 같이 멈추고, 결제가 느리면 주문도 함께 느려지며, 결제 서버를 교체할 때 주문 코드까지 함께 수정해야 한다.

디커플링의 핵심은 **서로 기다리지 말자**는 것이다. 서버 A는 서버 B의 작업이 끝날 때까지 기다리지 않고, 대신 할 일만 맡긴 뒤 B가 나중에 처리하도록 만든다. 이 구조를 위해서는 중간에 작업을 잠시 보관할 저장소가 필요하다.

```text
보내는 사람 ---> 택배센터 ---> 받는 사람
```

택배 시스템을 예로 들면, 보내는 사람은 받는 사람이 집에 있는지 신경 쓰지 않고 택배를 보내며, 받는 사람은 도착했을 때 택배를 받으면 된다. 이것이 디커플링 구조다.

**트레이드오프**: 디커플링이 항상 공짜로 얻어지는 이점은 아니다. 중간에 큐나 토픽 같은 컴포넌트가 추가되므로 최종 사용자 입장에서는 처리 결과를 즉시 받지 못하고 약간의 지연(Latency)이 생길 수 있으며, 구성 요소가 하나 늘어나는 만큼 모니터링·운영 대상도 늘어난다. 따라서 모든 통신을 무조건 디커플링해야 하는 것은 아니며, 응답을 즉시 받아야 하는 동기(Synchronous) 요청(예: 로그인 인증)과 비동기로 처리해도 되는 작업(예: 이미지 리사이징, 이메일 발송)을 구분해 필요한 곳에만 적용하는 것이 실무적인 접근이다.

**정리**: 디커플링은 두 시스템을 직접 연결하는 대신 중간 저장소를 두어 서로의 상태를 기다리지 않게 만드는 설계 방식이며, 이를 통해 아키텍처의 유연성(Flexibility)을 높이고 효율적인 변경·확장을 가능하게 하며 시스템 안정성을 강화하는 것을 목표로 한다.

## 2. 결합(Coupling)의 유형

시스템 간의 연결 강도는 **긴밀한 결합(Tight Coupling)**과 **느슨한 결합(Loose Coupling)** 두 가지로 구분할 수 있다.

- **긴밀한 결합(Tight Coupling)**: 서로 강하게 묶여 있는 상태로, 의존성이 높아 한쪽을 변경하면 다른 쪽도 반드시 수정해야 한다. 시스템이 단단히 묶여 있어 확장·변경이 어렵다. 비유하자면 사람의 몸과 같다 — 심장, 폐, 신경이 서로 강하게 연결되어 있어 한 부분에 문제가 생기면 전체에 영향을 준다.
- **느슨한 결합(Loose Coupling)**: 서로 느슨하게 연결된 상태로, 의존성이 낮아 독립적으로 동작할 수 있다. 쉽게 변경하거나 대체할 수 있어 더 유연한 아키텍처를 구현할 수 있다. 비유하자면 표준 공구나 로봇과 같다 — 부품을 교체해도 전체 시스템은 계속 작동한다.

**두 결합 방식 비교**

| 구분 | 긴밀한 결합(Tight Coupling) | 느슨한 결합(Loose Coupling) |
|---|---|---|
| 의존성 | 서로의 상태·응답을 직접 기다림 | 중간 저장소를 통해 비동기로 연결 |
| 장애 전파 | 한쪽이 멈추면 전체가 함께 멈춤 | 한쪽이 멈춰도 메시지가 보존되어 나중에 처리 가능 |
| 변경 영향 | 한쪽 수정 시 연결된 다른 쪽도 함께 수정 필요 | 각자 독립적으로 배포·변경 가능 |
| 확장성 | 트래픽 증가 시 전체 구조를 함께 스케일링해야 함 | 각 구성 요소를 필요에 따라 개별적으로 확장 가능 |
| 초기 구축 속도 | 빠르게 연결 가능(중간 계층 불필요) | 큐·토픽 등 추가 구성 요소 설계·운영 필요 |

클라우드 아키텍처에서 느슨한 결합(디커플링)의 대표적인 예시는 다음과 같다.

- **S3 + Lambda**: S3에 파일이 업로드되면 Lambda가 자동으로 실행되며, S3와 Lambda는 각각 독립적으로 변경될 수 있다.
- **SNS + SQS**: 발행/구독 모델을 통해 서비스 간 의존성을 줄인다.
- **마이크로서비스(MSA)**: 서비스별로 독립적인 배포와 확장이 가능하다.

**정리**: 긴밀한 결합은 빠른 통합은 가능하지만 변경과 확장이 어렵고, 느슨한 결합(디커플링)은 독립성과 유연성을 확보해 클라우드 아키텍처에 최적화된 방식이다.

## 3. 디커플링 주요 서비스 개요

AWS에서 디커플링을 구현할 때 사용하는 대표적인 서비스는 Amazon SQS, Amazon SNS, Amazon Kinesis 세 가지다.

- **Amazon SQS (Simple Queue Service)**: 완전관리형 메시지 큐 서비스다. 생산자(Producer)는 메시지를 큐에 넣고, 소비자(Consumer)는 큐에서 메시지를 꺼내 처리한다. 메시지 순서 보장(FIFO 큐 지원), 메시지 중복 방지, 뛰어난 확장성과 내구성이 특징이며, 주문 시스템에서 요청을 큐에 쌓아 두고 뒷단 서비스가 순차적으로 처리하는 방식으로 활용된다.
- **Amazon SNS (Simple Notification Service)**: 발행/구독(Pub/Sub) 기반 알림 서비스다. 하나의 메시지를 메일, SMS, Lambda, SQS 등 여러 구독자에게 동시에 전달한다. 푸시 기반 메시징 방식이며 다양한 프로토콜을 지원한다. 특정 이벤트가 발생했을 때 여러 시스템에 동시에 알림을 보내는 용도로 활용된다.
- **Amazon Kinesis**: 실시간 데이터 스트리밍 처리 서비스로, 초당 수백만 건 이상의 데이터 이벤트를 실시간으로 수집하고 분석할 수 있다. 대규모 로그, IoT, 스트리밍 데이터 처리에 적합하며 Athena, Redshift, QuickSight 같은 분석·시각화 서비스와 연계할 수 있다. 실시간 클릭 로그 분석, 주식 시세 데이터 처리 등에 활용된다.

SNS에 대한 심화 내용은 별도 문서에서 다루며, 이 문서에서는 SQS를 중심으로 심화한다.

**세 서비스 빠른 비교**

| 구분 | SQS | SNS | Kinesis |
|---|---|---|---|
| 전달 모델 | Pull(소비자가 가져감) | Push(즉시 밀어넣음) | Pull(Shard 단위로 스트림 읽기) |
| 소비자 수 | 여러 Consumer가 경쟁적으로 소비(메시지는 한 번만 처리됨) | 여러 Subscriber가 각각 전체 메시지를 수신 | 여러 Consumer가 동시에 같은 데이터를 읽고 재생(Replay) 가능 |
| 순서 보장 | FIFO Queue에서만 보장 | FIFO Topic에서만 보장 | Shard 내에서는 순서 보장 |
| 메시지 보관 | 최대 14일 | 저장하지 않음(SQS와 결합해야 보관 가능) | 기본 24시간, 설정에 따라 최대 365일까지 연장 가능 |
| 주 용도 | 작업 큐, 생산자·소비자 디커플링 | 하나의 이벤트를 여러 대상에 동시 통지(Fan Out) | 대용량 실시간 이벤트 스트림 수집·분석 |

즉 "누가 순서대로 하나씩 가져가서 처리해야 하는가"는 SQS, "하나의 이벤트를 여러 곳에 동시에 알려야 하는가"는 SNS, "끊임없이 쏟아지는 대량의 이벤트를 실시간으로 분석해야 하는가"는 Kinesis가 담당한다고 구분하면 이해하기 쉽다.

**정리**: SQS는 메시지를 순서대로 안전하게 전달하는 큐, SNS는 여러 대상에 동시에 알리는 발행/구독 서비스, Kinesis는 대용량 실시간 스트림을 처리하는 서비스로 역할이 구분되며, 세 서비스 모두 서버 간 직접 연결을 없애는 디커플링 서비스라는 공통점을 가진다.

## 4. Amazon SQS 개요와 동작 원리

**Amazon SQS**는 서버와 서버 사이에 메시지를 잠시 보관해 주는 중간 저장소 서비스다. 서버들이 서로 직접 연결되지 않고 SQS를 통해서만 데이터를 주고받도록 만들어 시스템을 안정적으로 운영하기 위해 사용한다.

```text
웹서버(Apache) ---> 처리서버(Tomcat) ---> DB
```

기존 구조에서는 한 서버라도 장애가 나면 전체 서비스가 같이 멈춘다. 반면 SQS를 중간에 둔 구조는 다음과 같다.

```text
웹서버 ---> SQS ---> 처리서버 ---> DB
```

이 구조에서는 처리서버가 잠시 멈춰도 데이터는 SQS에 남아 있고 나중에 다시 처리할 수 있다.

SQS의 가장 큰 목적은 세 가지다. 첫째, 서버 장애가 나도 데이터가 사라지지 않게 한다. 둘째, 요청이 몰릴 때 서버가 다운되지 않도록 부하를 나눈다. 셋째, 서버끼리 직접 묶이지 않게 해서 구조를 단순화한다.

SQS의 실제 동작 순서는 다음과 같다. 1단계, Producer가 메시지를 SQS에 보낸다. 2단계, 메시지는 Queue에 저장된다. 3단계, Consumer가 메시지를 가져간다. 4단계, 가져간 메시지는 잠시 숨김 처리된다(Visibility Timeout). 5단계, 처리에 성공하면 삭제한다. 6단계, 삭제하지 못하면 메시지는 다시 큐로 돌아온다. 이 구조 덕분에 자동 재처리가 가능하다.

SQS의 주요 특징은 다음과 같다.

- 메시지를 즉시 처리하지 않고 일정 시간 대기 후 전달하는 **지연 처리**가 가능하다.
- 초당 수십만 건 이상의 메시지를 처리할 수 있는 **확장성**을 갖는다.
- KMS 기반 암호화와 IAM 권한 제어를 지원하는 **보안** 기능을 제공한다.
- 여러 소비자가 같은 메시지를 요청해도 최종적으로 한 번만 처리되도록 설계된 **중복 최소화** 기능을 갖는다.
- 생산자와 소비자가 동시에 작동할 필요 없이 독립적으로 운영되는 **느슨한 연결(Decoupling)** 구조를 제공한다.
- 메시지 손실을 방지하고, FIFO 큐를 통해 순서를 보장하는 **처리 보장**을 제공한다.

SQS의 동작 방식은 메시지 저장(최대 14일 보관 가능), 메시지 전달(소비자가 요청하면 들어온 순서대로 전달하며 표준 큐는 대체로 순서를 보장하고 FIFO 큐는 엄격히 보장), 메시지 처리 후 삭제(ACK를 보내면 삭제), 오류 처리(일정 시간 안에 ACK를 보내지 못하면 다시 큐로 반환), 한 번만 전달(여러 소비자가 요청해도 최종적으로 한 번만 처리)로 구성된다.

**여러 Consumer가 하나의 Queue를 처리하는 구조**: 실무에서는 Consumer를 한 대만 두지 않고, Auto Scaling Group 등으로 여러 대를 동시에 운영하는 경우가 많다.

```text
Producer ---> SQS Queue ---> Consumer #1
                         ---> Consumer #2
                         ---> Consumer #3
```

이 구조에서 Consumer들은 서로 다른 메시지를 "경쟁적으로" 가져간다. 즉 하나의 메시지는 여러 Consumer 중 한 곳에서만 가져가 처리되며(다른 Consumer에게는 Visibility Timeout 동안 숨겨짐), Consumer 수가 늘어날수록 동시에 처리할 수 있는 메시지 수도 늘어나 처리량이 수평적으로 확장된다. 큐에 쌓인 메시지 수(`ApproximateNumberOfMessages`)를 CloudWatch 지표로 확인해 Auto Scaling 정책의 기준으로 삼는 것이 대표적인 활용 패턴이다.

**정리**: SQS는 서버 간 직접 연결을 없애는 중간 저장소로, Producer가 메시지를 넣고 Consumer가 꺼내 처리한 뒤 삭제하는 흐름을 통해 장애 격리·부하 분산·구조 단순화라는 세 가지 목적을 동시에 달성한다.

## 5. Standard Queue와 FIFO Queue

Amazon SQS의 큐 유형은 **Standard Queue**와 **FIFO Queue** 두 가지로 나뉜다.

**Standard Queue**는 처리 속도가 매우 빠르며 무제한 처리량을 지원한다. 다만 순서를 보장하지 않고, 메시지를 중복해서 전달할 수 있다(At Least Once Delivery). 대규모 트래픽을 처리하기에 적합하고 빠른 전송과 확장성을 보장한다는 장점이 있지만, 동일 메시지가 여러 번 전달될 수 있으므로 애플리케이션 레벨에서 멱등성(Idempotency)을 반드시 보장해야 한다. 일반적인 웹 서비스에서는 속도가 가장 중요할 때 대부분 Standard Queue를 사용한다.

**FIFO Queue(First-In-First-Out)**는 먼저 들어온 메시지가 먼저 처리되도록 메시지 순서를 완벽하게 보장하며, 메시지를 단 한 번만 전달한다(Exactly Once Processing). 성능은 Standard Queue에 비해 제한적이며 초당 처리량에도 제한이 있다. 순서가 중요한 결제, 예약, 금융 트랜잭션 같은 애플리케이션에 적합하고, 중복 메시지가 발생하지 않아 멱등성 고려가 줄어든다는 장점이 있지만, 성능이 제한적이므로 고성능 처리가 필요한 경우에는 적합하지 않을 수 있다. 결제, 금융, 정산 시스템처럼 정확성이 가장 중요할 때 주로 사용한다.

속도가 중요하면 Standard, 정확성이 중요하면 FIFO를 쓴다는 것이 기본 선택 기준이다.

| 구분 | Standard Queue | FIFO Queue |
|---|---|---|
| 처리량 | 무제한(높음) | 제한적(낮음) |
| 순서 보장 | 보장하지 않음 | 완벽히 보장 |
| 중복 메시지 | 발생 가능(At Least Once) | 없음(Exactly Once) |
| 적합한 사용 사례 | 대규모 트래픽 처리, 일반 웹 서비스 | 결제, 예약, 금융 트랜잭션 |

**주의사항**: FIFO Queue는 초당 처리량에 제한이 있다는 점을 설계 초기에 놓치기 쉽다. "순서 보장이 필요하다"는 이유만으로 별다른 검토 없이 FIFO Queue를 선택했다가, 실제 트래픽이 몰리는 운영 단계에서 처리량 한계에 부딪혀 병목이 발생하는 경우가 실무에서 흔히 나타난다. 이런 경우에는 Message Group ID를 여러 개로 나누어 병렬 처리 단위를 늘리거나, High Throughput 모드를 활성화해 완화할 수 있다(단, 상한치는 리전마다 다르므로 사전 확인이 필요하다). 전체 트래픽 중 순서 보장이 정말 필요한 일부 메시지만 FIFO로 분리하고, 나머지는 Standard Queue로 처리하는 하이브리드 설계도 자주 쓰인다.

**정리**: Standard Queue는 속도와 처리량을, FIFO Queue는 순서와 정확성을 우선하는 큐이며, 두 유형 중 무엇을 선택하느냐에 따라 멱등성 구현 필요성도 달라진다. 다만 FIFO를 고를 때는 처리량 제한을 감안한 트래픽 설계가 함께 필요하다.

## 6. 멱등성(Idempotency)

**멱등성(Idempotency)**은 같은 요청이 여러 번 실행되더라도 최종 결과가 동일하게 유지되는 성질을 말한다.

Standard Queue에서는 메시지가 여러 번 전달될 수 있기 때문에 멱등성 구현이 필수다. FIFO Queue는 중복 방지가 내장되어 있지만, 안정성을 위해 멱등성을 함께 구현하는 것이 권장된다.

멱등성이 필요한 대표적인 예로는 버스 표 구매와 파일 업로드가 있다. 같은 좌석을 여러 번 결제 시도하더라도 실제 결제는 한 번만 일어나야 하며, 같은 파일이 여러 번 업로드 요청되더라도 최종적으로는 한 번만 저장되어야 한다.

| 구분 | Standard Queue | FIFO Queue |
|---|---|---|
| 순서 보장 | X | O |
| 중복 메시지 | 발생 가능(At Least Once) | 없음(Exactly Once) |
| 처리량 | 무제한(높음) | 제한적(낮음) |
| 멱등성 필요성 | 반드시 필요 | 상대적으로 덜 필요하지만 권장 |
| 적합한 사용 사례 | 대규모 로그 처리, 알림 전송 | 결제, 예약, 주문 시스템 |

**구현 방법 예시**: 멱등성은 보통 애플리케이션 레벨에서 고유한 Idempotency Key(예: 주문 ID, 결제 요청 ID)를 두는 방식으로 구현한다. Consumer가 메시지를 처리하기 전, DB에 해당 키로 이미 처리된 기록이 있는지 먼저 확인하고, 있으면 처리를 건너뛰고 없으면 처리 후 키를 기록한다. 이때 "확인 후 기록" 과정이 원자적(atomic)으로 수행되도록 DB의 유니크 제약조건(Unique Constraint)이나 조건부 쓰기(Conditional Write, 예: DynamoDB의 `ConditionExpression`)를 함께 사용하는 것이 안전하다. 단순히 애플리케이션 코드에서 조회(SELECT) 후 삽입(INSERT)하는 방식만 쓰면, 두 개의 Consumer가 동시에 같은 메시지를 처리할 때 둘 다 "아직 처리 안 됨"으로 조회해버리는 경쟁 조건(Race Condition)이 발생할 수 있다.

**정리**: 멱등성은 중복 실행에도 결과가 바뀌지 않도록 만드는 설계 원칙이며, 큐 유형과 무관하게 애플리케이션 레벨에서 갖추어 두는 것이 안전한 시스템 운영의 기본이다. 특히 중복 확인과 처리 기록은 원자적으로 묶어야 동시 처리 상황에서도 안전하다.

## 7. S3+Auto Scaling의 한계와 SQS를 통한 해결

동영상 처리 서비스를 예로 들어 SQS 없이 S3와 Auto Scaling만 사용하는 구조의 한계를 살펴본다.

```text
사용자 ---> S3(원본) ---> EC2(처리) ---> S3(결과물)
```

이 구조에서는 오토 스케일링 그룹에 속한 EC2 인스턴스들이 새로운 동영상이 업로드되었는지를 계속 확인해야 하며, 다음과 같은 문제가 발생한다.

- **지속적인 체크 필요**: EC2 인스턴스들이 S3를 계속 모니터링해야 하므로 불필요한 자원 낭비가 발생한다.
- **중복 처리 가능성**: 여러 인스턴스가 동시에 같은 파일을 가져오려고 시도할 수 있어 중복 작업, 충돌, 동기화 문제가 생긴다.
- **장애 발생 시 로직 중단**: EC2 인스턴스가 죽으면 작업이 끊기고, 업로드된 영상이 제대로 처리되지 않는다.
- **스케일링 기준 불명확**: 영상 업로드 속도를 미리 알 수 없어 어떤 기준으로 Auto Scaling을 해야 할지 애매하며, CPU 사용률이나 시간 기준만으로는 트래픽 폭주 상황을 예측하기 어렵다.

이 문제는 SQS를 중간에 두는 방식으로 해결할 수 있다.

```text
사용자 ---> S3(원본) ---> SQS ---> EC2(처리, Auto Scaling) ---> S3(결과물)
```

사용자가 영상을 업로드하면 S3에 저장되고, S3는 업로드 이벤트를 SQS Queue에 메시지로 전달해 어떤 파일이 업로드되었는지 알린다. Auto Scaling Group의 EC2 인스턴스들은 Queue를 모니터링하여 메시지를 가져오고, 처리가 완료된 메시지만 정상적으로 삭제되어 큐에서 제거된다.

Queue에 쌓인 메시지 수를 기준으로 Auto Scaling이 동작한다. 메시지가 많으면 인스턴스 수를 늘려 빠르게 처리하고, 메시지가 적으면 줄여 비용을 절감한다. 또한 EC2 인스턴스가 갑자기 죽더라도 메시지는 Queue에 남아 있기 때문에 다른 인스턴스가 이어서 처리할 수 있다.

S3 + SQS + Auto Scaling 구조를 사용하면 불필요한 체크 제거, 중복 처리 방지, 안정적인 장애 대응, 메시지 기반 Auto Scaling이 가능해진다. 대규모 동영상 업로드·처리 서비스 같은 경우에는 SQS를 반드시 중간에 두는 구조가 가장 적합하다.

**주의사항**: SQS 없이 EC2가 S3를 직접 Polling하는 방식은 확인 주기를 짧게 잡을수록 새 파일을 빠르게 감지할 수 있지만, 그만큼 S3에 대한 요청 횟수가 늘어나 불필요한 요청 비용과 API 호출 부하가 커진다. 반대로 확인 주기를 길게 잡으면 비용은 줄지만 처리 지연이 커진다. SQS를 사용하면 S3가 업로드 이벤트를 직접 밀어주기(Push) 때문에 이런 폴링 주기 딜레마 자체가 사라진다는 점도 SQS 도입의 실질적인 이점이다.

**정리**: S3와 Auto Scaling만으로 구성한 처리 파이프라인은 지속적 폴링, 중복 처리, 장애 시 작업 유실, 불명확한 스케일링 기준이라는 네 가지 한계를 갖지만, SQS를 중간에 두면 메시지 수 기준의 Auto Scaling과 장애 시 재처리가 가능해져 이 한계를 모두 해소할 수 있다.

## 8. SQS 주요 구성 요소

Amazon SQS는 메시지, Producer, Queue, Consumer, DLQ, 액세스 정책이라는 여섯 가지 구성 요소로 이루어진다.

- **메시지(Message)**: SQS에서 전달되는 데이터의 가장 작은 단위다. Producer가 보낸 정보는 전부 메시지 형태로 만들어져 SQS에 저장된다. 주문 시스템이라면 주문번호·상품번호·금액·사용자 ID, 로그 시스템이라면 접속 시간·IP 주소·에러 내용이 메시지가 된다. 형태는 문자열, JSON, XML 등 다양하지만 실무에서는 대부분 JSON 형태를 사용하며, Consumer가 가져갈 때까지 Queue 안에서 대기 상태로 보관된다.
- **Producer(생산자)**: 메시지를 만들어서 SQS로 보내는 주체로, 웹 애플리케이션·IoT 기기·로그 수집 서버 등이 해당한다. 메시지를 보내고 나면 이후 처리는 전혀 신경 쓰지 않는 비동기 구조로 동작한다. Producer는 Consumer가 살아있는지, 처리했는지 모르며 오직 SQS에만 메시지를 보낸다.
- **Queue(대기열)**: 메시지를 임시로 저장하는 공간으로, SQS에서 가장 핵심이 되는 부분이다. 메시지 보관, 순서 관리, 중복 관리, 재전송 관리, 대기 관리 역할을 수행하며, Standard Queue와 FIFO Queue 두 종류가 있다.
- **Consumer(소비자)**: Queue에서 메시지를 가져가 처리하는 주체로, 주문 처리 서버·로그 분석 서버·메일 발송 서버·알림 서버 등이 해당한다. Consumer는 큐에서 메시지를 가져오고, 메시지 내용을 읽은 뒤, 프로그램 로직으로 처리하고, DB에 저장하거나 작업을 수행한 다음, 처리 완료 후 메시지를 삭제하는 순서로 동작한다. 삭제하지 않으면 SQS는 아직 처리되지 않은 것으로 판단해 자동 재처리를 수행할 수 있다.
- **DLQ(Dead Letter Queue)**: 계속 실패하는 메시지를 모아두는 전용 Queue다. 어떤 메시지가 여러 번 처리에 실패하면(예: 5번 연속 실패) 일반 Queue에서 빼서 DLQ로 이동시킨다. DLQ는 에러 원인 분석, 문제 데이터 확인, 버그 수정, 수동 재처리를 위한 문제 있는 메시지의 격리소 역할을 하며, DLQ가 없으면 에러 메시지가 계속 반복 처리되면서 시스템이 불안정해진다.

  **Redrive Policy 설정 예시**: DLQ를 사용하려면 원본 큐(Source Queue)에 Redrive Policy를 설정하여 어떤 DLQ로 보낼지, 몇 번 실패하면 이동시킬지(`maxReceiveCount`)를 지정해야 한다.

  ```json
  {
    "deadLetterTargetArn": "arn:aws:sqs:ap-northeast-2:123456789012:my-queue-dlq",
    "maxReceiveCount": 5
  }
  ```

  이 설정은 메시지가 5번 연속으로 Visibility Timeout 안에 삭제되지 못하고(처리에 실패하고) 큐로 돌아오면, 6번째 수신 시도 전에 자동으로 `my-queue-dlq`로 이동시킨다는 의미다. **Redrive Policy를 설정하지 않으면 실패한 메시지가 DLQ로 격리되지 않고 원본 큐에서 Visibility Timeout이 끝날 때마다 무한히 재시도되며, 이는 Consumer 자원을 계속 소모시키고 정상 메시지 처리까지 지연시키는 문제로 이어진다.** 실무에서는 DLQ 자체는 생성해 두고 정작 원본 큐의 Redrive Policy 연결을 빠뜨리는 실수가 자주 발생하므로, DLQ를 만들었다면 반드시 원본 큐의 Redrive Policy에도 연결되어 있는지 확인해야 한다.

- **액세스 정책(Access Policy)**: 누가 SQS에 접근 가능한지(EC2만 수신 가능, 특정 계정만 접근 가능 등)를 제한하는 정책이다. IAM 정책 기반으로 관리하며 JSON 형태로 작성하고, 설정하지 않으면 외부에서 마음대로 접근할 수 있기 때문에 반드시 설정해야 한다.

  **액세스 정책 예시**: 특정 계정의 특정 역할만 큐에 메시지를 보낼 수 있도록 제한하는 정책은 다음과 같은 형태를 가진다.

  ```json
  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Sid": "AllowSendFromSpecificRole",
        "Effect": "Allow",
        "Principal": { "AWS": "arn:aws:iam::123456789012:role/OrderServiceRole" },
        "Action": "sqs:SendMessage",
        "Resource": "arn:aws:sqs:ap-northeast-2:123456789012:my-queue"
      }
    ]
  }
  ```

  이 정책은 `OrderServiceRole`을 가진 주체만 `my-queue`에 메시지를 보낼 수 있도록 허용하며, 명시되지 않은 주체는 기본적으로 거부된다.

즉 Producer → Queue → Consumer 흐름으로 메시지가 전달되고, 실패 메시지는 DLQ로 분리되며, 모든 접근은 액세스 정책으로 제어된다.

**정리**: SQS의 여섯 가지 구성 요소는 각각 메시지를 생성(Producer)하고, 보관(Queue)하고, 처리(Consumer)하고, 실패한 메시지를 격리(DLQ)하고, 접근을 통제(액세스 정책)하는 역할을 나누어 맡으며, 이 요소들이 맞물려 안정적인 메시지 전달 구조를 만든다.

## 9. SQS 메시지의 세 가지 상태와 메시지 구성

메시지(Message)는 SQS에서 전달되는 데이터의 단위로, "주문번호 1234 처리 요청", "영상 파일 A 업로드 완료" 같은 형태를 가진다. 메시지를 통해 Producer와 Consumer는 직접 연결되지 않고 비동기적으로 통신할 수 있다.

메시지의 최대 크기는 1MiB(Mebibyte, 1024×1024=1,048,576 Byte로, 1MB=1,000,000 Byte와는 구분된다)이며, 저장 기간은 최대 14일까지 가능하고 기본값은 4일이다. 크기가 더 큰 데이터를 전송해야 할 경우에는 S3와 연동한 뒤 SQS에는 메타데이터만 저장하는 방식을 사용한다.

메시지는 **Stored(저장됨)**, **In Flight(처리 중)**, **Deleted(삭제됨)**의 세 가지 상태를 거친다.

- **Stored(저장됨)**: Producer가 메시지를 SQS Queue에 성공적으로 전달한 상태로, Queue에 대기 중이며 아직 Consumer가 가져가지 않은 상태다. 최대 건수 제한이 없어 무한히 메시지를 쌓아둘 수 있으며, 지정한 보관 기간(최대 14일) 동안 유지된다.
- **In Flight(처리 중)**: Consumer가 Queue에서 메시지를 가져가 처리 중인 상태로, 이때 메시지는 다른 Consumer에게 보이지 않으며 Visibility Timeout 기간 동안 숨겨진다. Visibility Timeout 내에 메시지를 삭제하지 않으면 다시 Queue로 돌아와 다른 Consumer가 처리할 수 있게 되어 중복 방지와 안정성을 동시에 확보한다. 동시 In Flight 메시지의 최대 개수는 Standard Queue가 약 120,000개, FIFO Queue가 약 20,000개다.

  **주의사항**: 이 한도에 도달하면 SQS는 추가로 메시지를 반환하지 않으며(`OverLimit` 오류), Consumer가 오래된 In Flight 메시지를 제때 삭제하지 못하고 계속 쌓아두는 구조라면 이 한도에 예상보다 쉽게 도달할 수 있다. Consumer 처리 로직에 오류가 있어 메시지를 삭제하지 못하고 계속 재시도만 반복하는 상황이라면, In Flight 메시지가 한도에 가까워지면서 신규 메시지 수신 자체가 막히는 장애로 이어질 수 있다. DLQ와 적절한 Visibility Timeout 설정이 이런 상황을 예방하는 안전장치 역할을 한다.
- **Deleted(삭제됨)**: Consumer가 메시지를 성공적으로 처리하고 삭제 요청(DeleteMessage)을 보낸 상태로, Queue에서 완전히 제거되어 더 이상 다른 Consumer가 접근할 수 없다.

메시지 상태는 `Producer ---> Queue에 메시지 저장(Stored) ---> Consumer가 가져와 처리 시작(In Flight) ---> 처리 완료 후 삭제 요청(Deleted)` 순서로 전환된다.

설계 시에는 Standard Queue에서는 같은 메시지가 두 번 전달될 수 있으므로 멱등성을 보장해야 한다는 점, 처리 시간이 긴 작업일수록 Visibility Timeout을 충분히 길게 조정해야 한다는 점, 여러 번 실패하는 메시지는 DLQ로 보내 추후 분석할 수 있다는 점을 함께 고려해야 한다.

SQS 메시지는 다음 요소로 구성된다.

1. **Message Body(메시지 본문)**: 실제 메시지의 데이터(String)로, Message Attribute를 포함해 최대 크기는 1MiB다. 콘텐츠가 큰 경우에는 동영상 파일을 직접 SQS에 담지 않고 S3에 저장한 뒤, SQS 메시지에는 해당 파일의 경로(URL 또는 키)만 포함하는 방식으로 처리한다.
2. **Message Attribute(메시지 속성)**: Key-Value 형식의 메타데이터로 Message Body에는 포함되지 않는다. 메시지의 분류, 필터링, 컨텍스트(Context) 제공이 주 용도이며(예: 영상 처리 알고리즘 명시, 분류를 위한 Tag 정의), 최대 10개까지 추가할 수 있다.

   ```json
   {
     "MessageBody": "{\"orderId\": 1234, \"status\": \"NEW\"}",
     "MessageAttributes": {
       "Algorithm": { "DataType": "String", "StringValue": "VideoAI" },
       "Priority": { "DataType": "Number", "StringValue": "1" }
     }
   }
   ```

   위 예시처럼 실제 업무 데이터는 Body에, 처리에 참고할 부가 정보는 Attribute에 나누어 담는 것이 일반적인 패턴이다.
3. **Message System Attribute(시스템 속성)**: AWS 서비스 내부에서 사용하는 시스템 메타데이터로, 현재는 AWS X-Ray 분산 추적을 위한 AWSTraceHeader만 지원한다.
4. **ReceiptHandle**: 메시지를 삭제하기 위해 사용하는 고유 키로, 메시지를 큐에서 삭제하려면 반드시 필요하다.
5. **기타 정보**: 메시지가 생성된 AWS 리전(Region), 메시지를 생성한 소스(Event Source), 메시지 본문 무결성 검증 해시값(MD5), 메시지 생성 시간(Timestamp).
6. **FIFO Queue 전용 속성**: 메시지를 그룹 단위로 처리할 수 있게 하는 식별자인 Message Group ID(같은 그룹 ID를 가진 메시지는 순차적으로 처리됨)와, 중복 메시지를 구분하기 위한 ID인 Deduplication ID(동일한 Deduplication ID를 가진 메시지는 중복으로 간주되어 5분 이내 재전송 시 큐에 추가되지 않음)가 있다.

**정리**: 메시지는 Stored → In Flight → Deleted의 세 상태를 거치며 처리되고, Message Body·Attribute·System Attribute·ReceiptHandle 등 여러 요소로 구성되므로, 상태 전환 규칙과 각 구성 요소의 역할을 함께 이해해야 멱등성·Visibility Timeout·DLQ 설계를 올바르게 할 수 있다.

## 10. SQS Producer와 Consumer

**Producer(메시지 생산자)**는 API를 통해 메시지를 Push 하는 방식으로 동작한다. 메시지를 전송하려면 반드시 Queue URL을 알아야 하며, 이는 Producer가 올바른 SQS Queue를 판별하여 메시지를 보낼 수 있도록 하는 식별자 역할을 한다. Queue URL은 리전(region), 계정 ID(account-id), 큐 이름(queue-name)으로 구성되며 기본 형식은 `https://sqs.<region>.amazonaws.com/<account-id>/<queue-name>`이다. 예를 들어 `https://sqs.us-east-1.amazonaws.com/123456789012/MyQueue`와 같은 형태를 가진다.

메시지를 전송하려면 `sqs:SendMessage` IAM 권한이 필요하다. IAM 사용자나 역할에 직접 권한을 부여하거나 리소스 기반 정책(Resource Policy)을 이용해 특정 Queue에 대한 접근 권한을 부여할 수 있으며, 권한이 없으면 메시지 전송이 실패한다.

SQS는 다양한 AWS 서비스와 이벤트 기반으로 연동할 수 있다. S3, SNS, Lambda 등 일부 서비스는 SQS와 직접 연결할 수 있고, EventBridge와 연동하면 더 정교한 이벤트 라우팅과 조건 처리가 가능하다. 예를 들어 S3에서 파일 업로드 이벤트를 SQS로 전송하거나, CloudWatch Alarm이 발생했을 때 SQS에 메시지를 생성하거나, EventBridge가 특정 조건의 이벤트만 SQS로 전달하는 방식으로 활용된다.

**직접 연동 vs EventBridge 경유**

| 구분 | 직접 연동(S3, SNS → SQS) | EventBridge 경유 |
|---|---|---|
| 설정 난이도 | 단순(이벤트 알림 설정만 추가) | 상대적으로 복잡(규칙·패턴 정의 필요) |
| 라우팅 유연성 | 소스 서비스가 정해준 이벤트 형태 그대로 전달 | 이벤트 내용을 세밀한 패턴으로 필터링하여 원하는 큐로만 라우팅 가능 |
| 다중 소스 통합 | 소스별로 개별 연동 설정 필요 | 여러 AWS 서비스·SaaS 이벤트를 한 버스에서 통합 관리 가능 |
| 적합한 상황 | 단순한 1:1 이벤트 전달 | 여러 이벤트 소스를 조건별로 서로 다른 큐·서비스로 분기해야 하는 경우 |

**Consumer(메시지 소비자)**는 큐에서 메시지를 가져와 처리하는 역할을 한다. 주기적으로 Poll 요청(API 호출)을 보내 큐에 메시지가 있는지 확인하며, 메시지를 받거나 삭제하려면 `sqs:ReceiveMessage`(메시지 받기)와 `sqs:DeleteMessage`(메시지 삭제) 권한이 필요하다.

Consumer의 기본 동작 흐름은 Poll → 처리 → 삭제다. Poll 단계에서 메시지를 큐에서 가져오고, 처리 단계에서 비즈니스 로직에 따라 메시지를 처리하며, 삭제 단계에서 처리가 끝난 메시지를 큐에서 삭제한다.

**정리**: Producer는 Queue URL과 `sqs:SendMessage` 권한을 가지고 메시지를 큐에 밀어 넣기만 하고, Consumer는 `sqs:ReceiveMessage`·`sqs:DeleteMessage` 권한을 가지고 Poll → 처리 → 삭제 흐름으로 메시지를 가져와 처리하며, Visibility Timeout 안에 삭제하지 않으면 메시지가 다시 큐로 돌아가 다른 Consumer에게 전달된다는 점을 함께 기억해야 한다.

## 11. Visibility Timeout

**Visibility Timeout(가시성 제한 시간)**은 한 Consumer가 메시지를 가져간 뒤, 다른 Consumer가 그 메시지를 가져갈 수 없도록 막는 시간이다. 일종의 잠금(Lock) 역할을 하며, 해당 시간 동안에는 다른 Consumer가 같은 메시지를 요청할 수 없다. 이는 메시지를 처리할 충분한 시간을 보장하기 위해 설정하는 값이다.

Visibility Timeout의 기본값은 30초이며, 최소값은 0초, 최대값은 12시간이다. 작업의 특성(빠른 처리인지, 오래 걸리는 처리인지)에 맞게 적절히 조정해야 한다.

처리 흐름은 다음과 같다. Consumer가 메시지를 가져오면 메시지는 Visibility Timeout 상태가 되고, 이 시간 안에 메시지를 처리한 뒤 삭제해야 한다. 만약 처리 중 문제가 생겨 삭제되지 않으면 시간이 지나면서 메시지가 다시 큐에 나타나 다른 Consumer가 가져갈 수 있게 된다.

Visibility Timeout은 큐 단위 또는 메시지 단위로 설정할 수 있으며, 필요할 때는 Consumer가 메시지를 처리하는 도중에 연장할 수도 있다. 설정 시간이 너무 짧으면 아직 처리 중인 메시지가 다시 큐에 나타나 중복 처리될 수 있고, 설정 시간이 너무 길면 실패한 메시지가 다른 Consumer에게 전달되기까지 불필요하게 오래 걸린다.

예를 들어 10초 내에 끝나는 간단한 로그 처리라면 Visibility Timeout을 기본값인 30초로 설정해도 충분하지만, 동영상 인코딩처럼 수 분 이상 걸릴 수 있는 작업은 Visibility Timeout을 몇 분 단위로 늘려야 중복 처리를 막을 수 있다.

**Visibility Timeout 연장(Heartbeat)**: 처리 시간이 가변적이거나 예상보다 길어질 수 있는 작업이라면, Consumer가 처리 도중 `ChangeMessageVisibility` API를 호출해 Visibility Timeout을 연장할 수 있다(일종의 하트비트 방식). 예를 들어 기본 Visibility Timeout을 60초로 설정했는데 실제 처리에 90초가 걸릴 수도 있는 작업이라면, 처리 중간에 주기적으로 Timeout 연장을 요청하여 다른 Consumer에게 메시지가 노출되는 상황을 방지해야 한다.

**주의사항**: Visibility Timeout을 처리 시간보다 짧게 설정하면, 아직 처리 중인 메시지가 다시 보이게 되어 다른 Consumer가 동일한 메시지를 중복으로 가져가 처리하는 문제가 발생한다. 예를 들어 이미지 리사이징에 평균 40초가 걸리는데 Visibility Timeout을 기본값인 30초로 그대로 두면, 처리 중인 메시지가 30초 뒤 다시 큐에 노출되어 다른 인스턴스가 동일한 파일을 다시 처리하는 중복 작업이 발생할 수 있다. 처리 시간을 미리 측정하고 여기에 여유(Buffer)를 더해 Visibility Timeout을 설정하는 것이 안전하다.

**정리**: Visibility Timeout은 기본 30초, 최소 0초, 최대 12시간 범위에서 설정하는 값으로, 작업 처리 시간에 맞춰 너무 짧지도 너무 길지도 않게 조정하는 것이 중복 처리와 지연 처리를 동시에 막는 핵심이다. 처리 시간이 가변적인 작업이라면 하트비트 방식의 연장까지 함께 고려해야 한다.

## 12. SQS Polling 방식(Short/Long)

SQS는 메시지를 자동으로 보내주지 않으며, 항상 서버가 먼저 할 일이 있는지 확인해야 하는데 이를 **Polling**이라고 한다. Amazon SQS는 내부적으로 여러 대의 서버에 메시지를 분산 저장하는 구조를 가진다 — 하나의 큐처럼 보이지만 실제로는 여러 서버에 나뉘어 저장되어 있다. 이 구조 때문에 Polling 방식이 필요하며, Short Polling과 Long Polling의 차이가 생긴다.

**Short Polling(기본 방식)**은 바로 확인하고 바로 돌아오는 방식으로, 기다리지 않는다. SQS는 내부 서버 중 일부만 확인하는데, 예를 들어 A 서버를 확인해 없으면 바로 없음을 응답하고, B 서버를 확인해 없으면 다시 없음을 응답하며, C 서버를 확인해 있으면 그때 받는 식으로 동작한다. 일부 서버만 조회하고 대기 시간이 없어 응답은 빠르지만 요청 횟수가 많아지고 비용이 증가하며, 메시지가 있어도 확인한 서버에 없으면 가져오지 못해 계속 재요청해야 한다. 이 때문에 특수한 경우가 아니면 거의 사용하지 않는다.

**Long Polling**은 처리 서버가 SQS에 메시지를 요청한 뒤, 바로 응답을 받지 않고 일정 시간(최대 20초) 동안 기다리는 방식이다. SQS에 메시지가 없으면 즉시 없음이라고 응답하지 않고 최대 20초까지 대기 상태를 유지한다. 여러 서버를 돌아다니며 확인하는 구조가 아니라 요청을 걸어둔 채 메시지가 생성될 때까지 대기하며, AWS 내부 시스템이 메시지가 들어오면 알려서 깨워주는 이벤트 기반 구조로 동작한다.

Long Polling의 동작 방식은 다음과 같다. 첫째, 처리 서버(EC2, Lambda 등)가 SQS에 요청한다. 둘째, SQS는 바로 응답하지 않고 요청을 대기 상태로 둔다. 셋째, 대기 중에 새로운 메시지가 들어오면 즉시 해당 메시지를 서버에게 전달한다. 넷째, 최대 대기 시간(최대 20초) 동안 메시지가 들어오지 않으면 없음으로 응답하고 연결을 종료한다.

**Short Polling의 비용 문제 예시**: Consumer가 계속 Short Polling으로 큐를 확인하는 구조라면, 메시지가 없을 때도 끊임없이 요청을 보내게 되어 요청 횟수가 급격히 늘어난다. 예를 들어 유휴 상태의 Consumer가 1초에 한 번씩 Short Polling 요청을 보낸다면 하루에만 86,400번의 요청이 발생하며, 이런 Consumer가 여러 대라면 요청 비용이 눈에 띄게 누적된다. Long Polling으로 전환하면 메시지가 없을 때는 최대 20초까지 연결을 유지한 채 대기하므로, 동일한 감시 기간 동안 발생하는 요청 횟수 자체가 크게 줄어들어 비용과 리소스 사용을 함께 절감할 수 있다. `ReceiveMessage` 호출 시 `WaitTimeSeconds` 파라미터를 0보다 크게 설정하면 Long Polling으로 동작한다.

**정리**: Short Polling은 일부 서버만 즉시 확인하고 끝내는 방식이라 메시지를 놓치기 쉽고 비용도 늘어나는 반면, Long Polling은 최대 20초까지 대기하며 메시지가 들어오는 즉시 전달받는 방식이라 대부분의 실무 환경에서는 Long Polling을 사용하는 것이 합리적이다.

## 13. DLQ 재처리(Redrive to Source)

DLQ에 쌓인 메시지는 그대로 방치하면 아무 의미가 없다. 원인을 분석하고 문제를 해결한 뒤에는 다시 정상적으로 처리될 수 있도록 원본 큐로 되돌려 보내는 절차가 필요하며, 이를 **Redrive to Source**라고 부른다.

**일반적인 재처리 흐름**

1. **원인 분석**: DLQ에 쌓인 메시지의 내용과 에러 로그(CloudWatch Logs 등)를 확인하여 왜 처리에 실패했는지 파악한다.
2. **원인 수정**: Consumer 코드의 버그, 잘못된 메시지 형식, 일시적인 외부 서비스 장애 등 실패 원인을 수정한다.
3. **재처리(Redrive)**: 콘솔 또는 API에서 DLQ 메시지를 원본 큐(또는 다른 지정한 큐)로 되돌려 다시 처리되도록 한다.
4. **모니터링**: 재처리된 메시지가 다시 DLQ로 돌아오지 않는지 확인하여 원인이 실제로 해결되었는지 검증한다.

**주의사항**: 원인을 파악하지 않은 채 무작정 재처리부터 시도하면 같은 이유로 다시 실패해 DLQ와 원본 큐 사이를 계속 오가는 낭비가 발생할 수 있다. 특히 메시지 자체에 문제가 있는 경우(잘못된 데이터 형식 등)라면 재처리 전에 메시지 내용을 직접 수정하거나 별도 로직으로 정제한 뒤 재전송하는 편이 안전하다.

**정리**: DLQ는 실패한 메시지를 모아두는 것에서 끝나지 않고, 원인 분석 → 수정 → 재처리 → 모니터링으로 이어지는 순환 구조를 통해 최종적으로 메시지가 정상 처리되도록 만드는 것이 목적이다.

## 14. SQS 설계 시 자주 놓치는 실무 포인트

지금까지 다룬 개념들을 실제 설계에 적용할 때 자주 놓치는 부분을 정리하면 다음과 같다.

| 놓치기 쉬운 부분 | 발생하는 문제 | 대응 방법 |
|---|---|---|
| FIFO 큐의 처리량 제한을 고려하지 않음 | 트래픽 증가 시 병목·지연 발생 | Message Group ID 분산, High Throughput 모드 검토, 순서가 꼭 필요한 메시지만 FIFO로 분리 |
| DLQ의 Redrive Policy 미설정 | 실패 메시지가 무한 재시도되며 Consumer 자원 낭비 | 원본 큐에 반드시 Redrive Policy(`maxReceiveCount`)를 연결 |
| Long Polling 미사용 | 불필요한 요청 급증, 비용 증가 | `WaitTimeSeconds`를 0보다 크게 설정 |
| Visibility Timeout을 처리 시간보다 짧게 설정 | 메시지 중복 처리 | 예상 처리 시간 + 여유 시간으로 설정, 필요 시 하트비트로 연장 |
| 메시지 크기(1MiB) 초과 데이터를 그대로 전송 시도 | 전송 자체가 실패함 | S3에 원본을 저장하고 메시지에는 참조 정보(버킷·키)만 포함(Claim Check 패턴) |

**정리**: SQS는 개념 자체는 단순하지만, FIFO 처리량 제한·DLQ 설정 누락·Polling 방식·Visibility Timeout 설정 같은 세부 사항을 놓치면 운영 단계에서 병목이나 중복 처리, 불필요한 비용 증가로 이어질 수 있다. 큐를 설계할 때는 이 다섯 가지 포인트를 체크리스트처럼 점검하는 것이 안전하다.

## 15. SQS와 Lambda 연동(Event Source Mapping)

SQS는 Consumer로 EC2 대신 Lambda 함수를 사용하는 서버리스 구조로도 자주 연동된다. 이때 Lambda가 큐를 직접 Polling하는 것이 아니라, AWS가 관리하는 **Event Source Mapping**이 백그라운드에서 큐를 Long Polling하며 메시지가 쌓이면 자동으로 Lambda 함수를 호출해 주는 방식으로 동작한다.

**주요 설정 항목**

| 설정 | 설명 |
|---|---|
| Batch Size | 한 번의 Lambda 호출에 담아 전달할 최대 메시지 개수 |
| Batch Window | 배치를 채우기 위해 기다리는 최대 대기 시간 |
| 동시성(Concurrency) | 큐에 메시지가 몰릴 때 Lambda가 동시에 몇 개까지 실행될 수 있는지에 대한 제한 |
| Maximum Concurrency | Event Source Mapping이 한 번에 호출할 수 있는 Lambda 실행 동시성의 상한을 별도로 지정하는 옵션 |

**부분 배치 실패(Partial Batch Failure)**: 하나의 배치에 여러 메시지를 묶어 Lambda에 전달했을 때, 그중 일부 메시지만 처리에 실패하는 경우가 있다. 이런 상황에서 Lambda 함수가 배치 전체를 실패로 처리해버리면, 이미 성공적으로 처리된 메시지까지 다시 재시도되어 중복 처리가 발생할 수 있다. 이를 방지하기 위해 Lambda의 `ReportBatchItemFailures` 기능을 활성화하면, 실패한 메시지의 ID만 정확히 지정해 응답할 수 있어 성공한 메시지는 정상적으로 삭제되고 실패한 메시지만 재시도 대상이 된다.

**FIFO 큐와 Lambda 연동 시 주의점**: FIFO 큐를 Lambda의 이벤트 소스로 사용할 경우, 같은 Message Group ID를 가진 메시지가 포함된 배치 중 하나라도 처리에 실패하면, 해당 그룹의 이후 메시지 처리가 그 실패가 해결될 때까지 지연된다. Standard 큐보다 오류 처리에 더 신경 써야 하는 이유다.

**정리**: SQS와 Lambda를 Event Source Mapping으로 연동하면 별도의 Polling 서버 없이도 서버리스 방식으로 메시지를 처리할 수 있지만, Batch Size·동시성 설정과 부분 배치 실패 처리(`ReportBatchItemFailures`)를 제대로 구성하지 않으면 중복 처리나 불필요한 재시도로 이어질 수 있으므로 세심한 설정이 필요하다.
