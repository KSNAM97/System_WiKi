# Amazon Route 53 Health Check와 Routing Policy

[AWS-T09. Route 53](t09-route53.md) 문서에서 다룬 기본 개념(레코드, Hosted Zone, Alias)을 먼저 참고하면 이해가 쉽다.

## 1. Health Check 개요

**Route 53 Health Check**는 Route 53에 등록된 리소스(웹 애플리케이션, 서버, API 엔드포인트 등)가 정상적으로 응답하는지 주기적으로 점검하는 기능이다. 단순히 "살아있는지"만 확인하는 것이 아니라, 그 결과를 라우팅 정책과 CloudWatch에 연결해 실제 트래픽 제어와 알림까지 이어지도록 설계되어 있다.

**주요 기능**

- **모니터링 및 알림**: 리소스가 정상 응답을 하지 않으면 비정상(Unhealthy) 상태로 판별한다. 이 결과는 가중치 라우팅, 장애 조치(Failover) 라우팅 등에서 트래픽 분배 판단 근거로 활용된다. Amazon CloudWatch와 연동하면 장애 발생 시 경보를 통해 알림을 받을 수 있다.
- **지연(Latency) 정보 확인**: TCP Connection 시간(서버와 TCP 연결을 맺는 데 걸린 시간), HTTP/HTTPS First Byte Latency(서버가 첫 응답 바이트를 보내기까지 걸린 시간), SSL/TLS Handshake 시간(HTTPS 연결 시 암호화 협상에 걸린 시간)을 각각 확인할 수 있다.
- **CloudWatch 연동**: Health Check 결과는 CloudWatch Metrics로 전달되어 대시보드에서 시각화할 수 있고, CloudWatch Alarm을 설정하면 실패 시 SNS 등을 통해 운영자에게 알림을 보낼 수 있다.
- **리전 제한**: Health Checker 자체는 미국 동부(버지니아 북부, `us-east-1`) 리전에서만 관리·운영된다. 다만 이는 Health Checker의 관리 리전이 그렇다는 의미이며, 실제로 점검 대상이 되는 리소스는 전 세계 어디에 있어도 상관없다.
- **활용 예시**: 장애 조치 라우팅(기본 서버 장애 시 자동으로 대체 서버로 전환), 성능 기반 라우팅(지연 시간이 짧은 리전으로 트래픽 분산), 경보/알림(리소스 장애 시 운영자에게 즉시 통보)

**정리**: Health Check는 리소스의 생존 여부를 판단하는 데 그치지 않고, 그 판단 결과를 라우팅 정책과 CloudWatch 경보 체계에 연결해 자동화된 장애 대응 파이프라인을 만드는 핵심 부품이다.

## 2. Health Check 모니터링 대상

Health Check가 점검할 수 있는 대상은 크게 세 가지로 나뉜다.

### 2-1. 특정 리소스

웹 서버, API 엔드포인트, 데이터베이스 등 개별 리소스의 상태를 직접 확인하는 방식이다. 예를 들어 EC2 인스턴스에서 실행 중인 웹 애플리케이션이 정상적으로 응답하는지를 확인하는 경우가 여기에 해당한다. 구체적인 점검 방식은 [3. 리소스 모니터링 방식](#3-리소스-모니터링-방식)에서 다룬다.

### 2-2. 다른 Health Check

하나의 Health Check 결과를 다른 Health Check의 입력값으로 사용할 수 있다. 여러 개의 Health Check를 조합해서 더 종합적인 상태 판정을 내릴 수 있다. 예를 들어 서로 다른 두 리전의 서버가 모두 정상일 때만 전체를 정상으로 판단하도록 구성할 수 있다. 조합 방식은 [5. 여러 Health Check 조합](#5-여러-health-check-조합)에서 자세히 다룬다.

### 2-3. Amazon CloudWatch 경보

CloudWatch Alarm의 상태 자체를 Route 53 Health Check로 모니터링할 수 있다. CPU, 메모리, 디스크, 네트워크 지연 같은 특정 메트릭 기반의 알람을 Health Check와 연동하면, 단순한 네트워크 응답 여부뿐 아니라 애플리케이션 내부의 성능 저하까지 Health Check 판정에 반영할 수 있다.

**정리**: Health Check는 "리소스에 직접 요청을 보내 확인"하는 방식 외에도, "다른 Health Check의 결과를 재사용"하거나 "CloudWatch Alarm 상태를 그대로 가져오는" 방식으로도 구성할 수 있다. 이 유연성 덕분에 단순 네트워크 점검을 넘어 서비스 전체의 건강 상태를 정의할 수 있다.

## 3. 리소스 모니터링 방식

특정 리소스를 점검할 때는 지정한 IP 주소나 도메인에 주기적으로 요청을 보내 응답 여부를 확인한다. 이 점검은 전 세계 여러 리전에 분산된 Health Checker 노드에서 동시에 수행되며, 미리 지정한 프로토콜(HTTP, HTTPS, TCP 등)과 주기에 맞춰 요청이 발송된다.

### 3-1. IP 주소 기반 모드

- IPv4/IPv6 주소를 모두 지원한다.
- 로컬 IP, Private IP, Multicast 주소는 Health Check 대상으로 지정할 수 없다.
- 점검 방식: HTTP/HTTPS는 2xx·3xx 상태 코드를 받으면 정상으로 판단하고, TCP는 연결이 수립되는지 여부만 확인한다.

### 3-2. 도메인 기반 모드

- IP 대신 도메인 이름을 입력해서 점검을 수행할 수 있다.
- 점검 방식은 IP 기반 모드와 동일하게 2xx·3xx 상태 코드를 확인한다.
- 제한사항: 도메인 기반 모드는 IPv4 주소만 지원한다(A 레코드만 지원). 즉 해당 도메인에 A 레코드가 없고 AAAA 레코드나 CNAME 레코드만 있는 경우에는 점검이 실패 처리된다.

### 3-3. 매칭 문자열 검사(String Matching)

단순히 상태 코드만 확인하는 것이 아니라, 응답 Body 안에 특정 문자열이 포함되어 있는지까지 검사할 수 있다. 예를 들어 응답 본문에 반드시 `"Success"`라는 문자열이 포함되어야만 Healthy로 판정하도록 설정할 수 있다. 서버가 200 OK를 반환하더라도 내부적으로 오류 페이지를 응답하는 경우까지 걸러낼 수 있어, 상태 코드만으로는 잡아내지 못하는 애플리케이션 레벨 장애를 탐지하는 데 유용하다.

### 3-4. Health Check Region

Health Check는 기본적으로 최소 3개 이상의 리전에서 동시에 수행된다. 전 세계 어디서든 공정하게 가용성을 판단하기 위해서다.

### 3-5. 기타 옵션

| 옵션 | 설명 |
|---|---|
| 포트(Port) 지정 | 점검할 포트를 직접 지정한다 (예: 80, 443, 8080 등). |
| 경로(Path) 지정 | HTTP/HTTPS 점검 시 확인할 경로를 지정한다 (예: `/health`, `/status`). |
| 요청 주기 | 10초 간격(추가 요금 발생) 또는 30초 간격(기본, Checker 간 동기화 없음) 중 선택한다. |
| Latency Graphs | 응답 지연 시간을 시각화한 그래프를 제공한다. |
| Inverse Check | 정상 응답일 때 오히려 Fail로, 비정상일 때 오히려 Healthy로 판정하는 역방향 로직이다. 유지보수 모드 감지 등 특수한 시나리오에 활용된다. |

**주의사항**: Health Check 대상이 AWS 외부 리소스(온프레미스 서버, 다른 클라우드의 엔드포인트 등)인 경우 추가 요금이 발생한다.

**정리**: 리소스 모니터링은 IP 기반이든 도메인 기반이든 결국 "상태 코드 확인 + 필요 시 문자열 검사"라는 두 축으로 이루어지며, 포트·경로·주기·Inverse Check 같은 옵션을 조합해 점검 조건을 세밀하게 맞출 수 있다.

## 4. Health 상태 판정 기준

Health Check가 대상을 Healthy 또는 Unhealthy로 판정하는 기준은 크게 두 가지 지표로 구성된다.

**1) 응답 속도**

| 점검 방식 | 임계 시간 |
|---|---|
| HTTP 연결 수립 | 4초 이내 |
| TCP 연결 수립 | 10초 이내 |
| HTTP String Match(문자열 검사) | 2초 이내에 값 확인 |

**2) 응답 내용 및 실패 횟수**

정상 응답이 특정 횟수 이상 연속으로 실패하면 해당 리소스는 비정상(Unhealthy)으로 판별된다.

**전체 Health 상태 판정 방식(18% 규칙)**

Route 53은 여러 리전에 분산된 다수의 Health Checker가 각각 점검을 수행한 뒤, 그 결과를 종합해서 최종 Health 상태를 판정한다. 이때 기준이 되는 규칙이 있는데, 전체 Health Checker 중 **18%를 초과하는 비율**이 정상 응답을 보내야만 해당 리소스가 전체적으로 Healthy 상태로 간주된다. 다시 말해 정상 응답 비율이 18% 이하로 떨어지면 리소스 전체가 Unhealthy로 판정된다. 이 수치는 Health Checker 노드 수가 리전별로 다르게 분산되어 있는 구조에서, 일부 리전의 일시적 네트워크 문제만으로 전체를 오판정하지 않도록 설계된 값이다.

**리전 제한**: Health Checker는 `us-east-1`(버지니아 북부) 리전에서만 관리되며, 이는 점검 인프라의 관리 위치일 뿐 점검 대상 리소스의 위치와는 무관하다.

**외부 리소스 추가 요금**: 점검 대상이 AWS 바깥의 리소스(온프레미스, 타 클라우드)라면 추가 요금이 부과된다.

**정리**: Health 상태는 "응답 속도 임계값을 지켰는가"와 "18% 규칙을 만족하는 비율의 Health Checker가 정상 응답을 보냈는가"라는 두 조건으로 결정된다. 특히 18% 규칙은 실무에서 자주 간과되는 부분이라 반드시 기억해 둘 필요가 있다.

## 5. 여러 Health Check 조합

단일 Health Check만으로는 서비스 전체의 가용성을 정확히 판단하기 어려운 경우가 많다. Route 53은 여러 개의 Health Check를 논리적으로 조합해서 하나의 판정 결과를 만들 수 있는 기능을 제공한다. 예를 들어 3개 이상의 Health Check 중 다수가 실패하면 장애로 간주하고 알림을 보내거나 Failover를 실행하도록 구성할 수 있다.

**조합 방식 3가지**

| 방식 | 판정 조건 | 특징 |
|---|---|---|
| **AND(모두 성공 시 성공)** | 모든 하위 Health Check가 성공해야 전체가 성공 | 예: 3개 서버 모두 응답해야 정상. 신뢰성은 높지만 하나만 실패해도 전체가 실패 처리됨 |
| **OR(하나라도 성공 시 성공)** | 하위 Health Check 중 하나라도 성공하면 전체가 성공 | 예: 3개 중 1개라도 살아있으면 정상. 고가용성 Active-Active 환경에서 주로 사용 |
| **Quorum(지정 개수 이상 성공 시 성공)** | 지정한 숫자 이상의 하위 Health Check가 성공해야 전체가 성공 | 예: 5개 중 최소 3개 이상 성공해야 정상. 과반수 개념으로 일정 수준의 가용성을 보장 |

**Health Check 조합의 논리 연산 예시**

여러 리전의 Health Check 결과를 조합할 때는 최소(Minimum)/최대(Maximum)/평균(Average) 같은 연산 개념으로도 이해할 수 있다. 예를 들어 도쿄=정상(1), 싱가포르=정상(1), 미국=비정상(0), 유럽=정상(1)이라는 4개 리전의 점검 결과가 있다고 가정하면 다음과 같이 해석할 수 있다.

- **최소(Minimum) 연산**: 하나라도 0(비정상)이 있으면 전체 결과가 0이 된다. 장애를 가장 민감하게 잡아내는 방식으로, 위 예시에서는 결과가 0(비정상)이 된다.
- **최대(Maximum) 연산**: 하나라도 1(정상)이 있으면 전체 결과가 1이 된다. 장애를 덜 민감하게 잡는 방식으로, 위 예시에서는 결과가 1(정상)이 된다.
- **평균(Average) 연산**: 전체 검사값의 평균을 낸다. 위 예시에서는 `[1, 1, 0, 1]`의 평균인 0.75가 되며, 부분적인 장애율을 파악하는 데 유용하다.

이런 조합 연산은 CloudWatch Alarm과 함께 활용되는 경우가 많은데, 이때 **기간(Period)** 개념이 함께 등장한다. Period는 CloudWatch가 지표를 집계하는 시간 단위로, 보통 1분(빠른 감지가 필요할 때) 또는 5분(더 안정적인 감지가 필요할 때) 단위를 사용한다.

**조합의 장점**

- 단순 리소스 모니터링보다 서비스 전체의 가용성 관점에서 상태를 판정할 수 있다.
- CloudWatch Alarm이나 Failover/Weighted 같은 라우팅 정책과 연동해 자동 대응을 구성할 수 있다.
- 글로벌 서비스 운영 시 일부 리전이나 서버의 문제만으로 전체 장애로 오판정하지 않도록 유연하게 설정할 수 있다.

**정리**: 여러 Health Check를 조합하는 것은 단일 지표로는 놓치기 쉬운 부분 장애를 정확히 반영하기 위한 방법이다. AND/OR/Quorum 중 어떤 방식을 쓸지는 "신뢰성을 얼마나 엄격하게 볼 것인가"와 "가용성을 얼마나 유연하게 볼 것인가"의 트레이드오프로 결정하면 된다.

## 6. Routing Policy 개요

**Routing Policy**는 도메인 레코드가 어느 리소스(EC2, ALB, S3, CloudFront 등)로 연결될지를 결정하는 방식이다. 단순히 DNS 이름을 IP로 매핑하는 것을 넘어, 트래픽 분산·장애 조치·성능 최적화까지 지원한다. Route 53은 아래 8가지 라우팅 정책을 제공한다.

1. Simple Routing
2. Failover Routing
3. Geolocation Routing
4. Geoproximity Routing
5. Latency-Based Routing
6. IP-based Routing
7. Multivalue Answer Routing
8. Weighted Routing

**정리**: 8가지 라우팅 정책은 크게 "단일 대상 연결(Simple)", "장애 대비(Failover)", "위치 기반 최적화(Geolocation, Geoproximity, Latency-Based, IP-based)", "트래픽 분산(Multivalue Answer, Weighted)"이라는 목적별로 묶어서 이해하면 각 정책의 쓰임새가 더 명확해진다. 각 정책의 세부 내용은 이어지는 절에서 다룬다.

## 7. Simple Routing Policy

가장 기본적인 라우팅 방식으로, 하나의 DNS 레코드를 하나의 대상 리소스로만 연결한다.

**동작 방식**: 트래픽 분산, 조건부 라우팅, 장애 조치 같은 부가 기능이 전혀 없다. 사용자가 도메인에 접속하면 항상 등록된 단일 IP·엔드포인트로만 응답한다.

**사용 사례**: 단일 서버 운영, 테스트/POC 환경, 소규모 개인 사이트

**장점**: 설정이 매우 간단하고 관리가 쉽다.

**한계**: 고가용성을 제공할 수 없다(서버가 다운되면 서비스 전체가 중단됨). 부하 분산이 불가능하다. 여러 리전에 걸친 글로벌 사용자 환경에는 적합하지 않다.

**정리**: Simple Routing은 "정말로 단순한 구성"이 필요할 때만 선택해야 하는 정책이며, 고가용성이나 트래픽 분산이 조금이라도 필요하다면 다른 정책으로 넘어가야 한다.

## 8. Failover Routing Policy

평소에는 모든 트래픽을 기본 대상(Primary)으로 라우팅하다가, 기본 대상에 장애가 발생하면 자동으로 보조 대상(Secondary)으로 전환하는 정책이다.

**동작 방식**: Health Check로 Primary 대상의 상태를 지속적으로 모니터링한다. Primary가 Fail 상태로 판정되면 자동으로 Secondary 대상으로 트래픽을 전환한다. Secondary는 평소에는 대기(Standby) 상태로 있다가, 필요할 때만 트래픽을 처리한다.

**사용 사례**: Active-Passive Failover(예: 서울 리전이 다운되면 도쿄 리전으로 자동 전환), 재해 복구(Disaster Recovery)

**장점**: 서비스 중단을 최소화할 수 있다. 운영자의 개입 없이 자동으로 장애 조치가 이루어진다. Secondary 대상은 필요할 때만 활성화되므로 비용을 절감할 수 있다.

**주의사항**: 반드시 Health Check와 함께 설정해야 정상적으로 동작한다. Secondary 대상은 언제 트래픽을 받아도 문제없도록 항상 최신 상태로 준비되어 있어야 한다. 여러 개의 Secondary 대상을 지정하는 것도 가능하지만, 일반적으로는 1차 Primary와 1차 Secondary로 구성하는 것이 가장 흔하다.

**정리**: Failover Routing은 Health Check가 반드시 짝을 이루어야 의미가 있는 정책이다. Health Check 없이 Failover 레코드만 만들면 장애 감지 자체가 되지 않아 자동 전환이 일어나지 않는다는 점을 기억해야 한다.

## 9. Geolocation Routing Policy

DNS 쿼리가 발생한 지역에 따라 서로 다른 응답을 반환하는 정책이다.

**설정 단위**: 대륙(Continent), 나라(Country), 그리고 미국의 경우 주(State) 단위까지 지정할 수 있다. 설정 범위가 겹치는 경우에는 더 세부적인 지역이 우선 적용된다. 예를 들어 "아시아"와 "한국"을 동시에 설정했다면, 한국에서 온 요청에는 "한국" 규칙이 적용된다.

**특징**: 관리자가 직접 지역과 리소스를 매핑해서 지정해야 한다. Route 53이 자동으로 가장 가까운 리전을 선택해 주지는 않는다.

**사용 사례**: 언어별 라우팅(현지화된 웹사이트 제공), 지역별 콘텐츠 구분(저작권 문제로 특정 국가에만 콘텐츠 제공), 인프라 최적화

**장점**: 지역에 맞춘 맞춤형 서비스를 제공할 수 있다. 불필요한 해외 트래픽을 줄일 수 있다. 데이터 지역 규제나 저작권 제한에 대응하기 쉽다.

**주의사항**: 지연 시간을 고려하는 자동 최적화 정책이 아니라 수동으로 설계하는 정책이다(이 점에서 Latency Routing과 구분된다). 지정되지 않은 지역에서 오는 요청을 위한 기본(Default) 응답을 반드시 별도로 설정해야 한다. 잘못 설계하면 특정 지역의 사용자가 아예 접근할 수 없는 상태가 될 수 있다.

**정리**: Geolocation Routing은 위치 기반 라우팅 중에서도 "관리자가 지역-리소스 매핑을 수동으로 결정"하는 정책이라는 점이 핵심이며, Default 라우팅을 빠뜨리면 미지정 지역 사용자가 서비스에 접근하지 못하는 사고로 이어질 수 있다.

## 10. Geoproximity Routing Policy

DNS 쿼리가 발생한 위치와 리소스(서버)가 위치한 곳을 동시에 고려해서, 가장 가까운 리소스로 트래픽을 라우팅하는 정책이다.

**Geolocation과의 차이**: Geolocation은 사용자의 위치만 보고 관리자가 지정한 규칙을 그대로 따르지만, Geoproximity는 리소스의 위치까지 함께 고려해서 근접도를 판단한다.

**Bias(편향값)**: 리소스별 커버리지 범위를 조정하는 값이다. 예를 들어 도쿄 리전에 양수(+) Bias를 부여하면 일본뿐 아니라 주변 아시아 일부 지역의 요청까지 도쿄로 유도할 수 있다. 반대로 음수(-) Bias를 부여하면 도쿄의 커버리지를 줄이고 트래픽을 다른 리전으로 분산시킬 수 있다.

**사용 사례**: 지역별 콘텐츠 제공(지연 시간 최소화), 부하 분산(Bias로 특정 리전에 트래픽이 몰리는 것을 방지), 글로벌 서비스 최적화

**장점**: 사용자 경험을 개선할 수 있다. Bias 값으로 트래픽 비율을 의도적으로 제어할 수 있다. 글로벌 서비스에 적합하다.

**주의사항**: Geoproximity Routing은 단순 DNS 레코드 수준에서 제공되지 않으며, Route 53 **Traffic Flow** 기능을 사용해야만 설정할 수 있다. Bias 설정을 잘못하면 특정 리전에 트래픽이 과도하게 집중될 수 있다.

**정리**: Geoproximity는 Geolocation보다 한 단계 더 정교한 위치 기반 라우팅이며, Bias라는 조정 가능한 변수를 통해 리전 간 트래픽 비율을 세밀하게 튜닝할 수 있다는 점이 가장 큰 특징이다.

## 11. Latency-Based Routing Policy

사용자를 기준으로 가장 빠른 네트워크 지연 시간(Latency)을 가진 리소스로 트래픽을 라우팅하는 정책이다.

**동작 방식**: Route 53이 여러 리전 간의 지연 시간을 측정해서, 요청이 들어올 때 가장 응답이 빠른 리전으로 연결한다. 예를 들어 도쿄와 버지니아 리전에 각각 ALB가 있을 때, 서울에서 요청이 발생하면 서울-도쿄와 서울-버지니아 사이의 지연 시간을 비교해서 더 빠른 쪽으로 라우팅한다. 이때 기준은 물리적 거리가 아니라 실제 네트워크 지연 시간이라는 점이 중요하다.

**특징**: 지연 시간 측정이 AWS 데이터센터 간 네트워크를 기준으로 이루어지기 때문에, AWS 인프라 외부의 네트워크 경로에서는 정확도가 떨어질 수 있다. Health Check와 함께 사용하면 "빠르면서도 정상 상태인" 리소스로만 트래픽을 보낼 수 있다.

**사용 사례**: 멀티 리전 서비스 최적화(글로벌 웹사이트, 스트리밍, 게임), Active-Active Failover 구조

**장점**: 사용자 경험을 개선할 수 있다. 여러 리전에 걸쳐 트래픽을 분산할 수 있다.

**주의사항**: 실제 사용자의 ISP나 인터넷 경로 품질에 따라 오차가 발생할 수 있다. 지연 시간이 빠르다고 해서 항상 비용 효율적인 것은 아니다. 측정 자체가 AWS 내부 네트워크 기준이라 외부 네트워크 상황이 반영되지 않을 수 있다.

**정리**: Latency-Based Routing은 "거리가 아니라 실측 지연 시간" 기준이라는 점이 핵심이며, Health Check와 결합하면 성능과 가용성을 동시에 챙길 수 있는 정책이 된다.

## 12. IP-based Routing Policy

사용자의 IP 주소(CIDR 대역)를 기준으로 트래픽을 세분화해서 라우팅하는 고급 정책이다.

**동작 방식**: Route 53이 요청을 보낸 사용자의 IP를 식별해서, 관리자가 미리 설정해 둔 CIDR 범위와 매칭한다. 매칭되는 대역의 요청은 지정된 리소스로, 그 외의 요청은 다른 리소스로 라우팅된다.

**사용 사례**: 특정 ISP 대역만 특정 리전으로 연결(예: 국내 통신사 대역은 서울 리전, 해외 ISP는 도쿄 리전), 기업 내부망 라우팅(사내 IP 대역만 개발 서버로 접속), 보안 강화(허용된 IP 대역만 특정 서비스에 접근, 예: 관리자 콘솔은 본사 IP 대역에서만 접속 가능)

**장점**: 사용자 그룹을 IP 기준으로 정확하게 분리할 수 있다. ISP, 기업망, 특정 고객사 전용 서비스 등 세밀한 라우팅이 가능하다. 보안과 접근 제어에 유용하다.

**주의사항**: CIDR 범위를 잘못 설정하면 정상 사용자까지 차단될 수 있다. IP는 언제든 변경될 수 있으므로 최신 정보를 유지해야 한다. IPv4/IPv6를 모두 관리할 수 있지만, 대역이 많아질수록 정책 관리가 복잡해질 수 있다.

**정리**: IP-based Routing은 "사용자가 어디서 왔는가"가 아니라 "사용자가 어떤 IP 대역에 속하는가"를 기준으로 삼는 정책으로, 보안 목적의 세밀한 접근 제어에 특히 유용하다.

## 13. Multivalue Answer Routing Policy

하나의 DNS 쿼리에 대해 여러 개의 IP 주소를 응답으로 반환하고, 클라이언트가 그중 하나를 무작위로 선택해서 연결하는 정책이다.

**동작 방식**: Route 53에 하나의 레코드에 여러 개의 리소스(IP·엔드포인트)를 등록해 두면, 클라이언트 요청 시 여러 IP가 함께 반환되고 대략 라운드 로빈처럼 분산되는 효과를 낸다. Health Check와 연동하면 비정상 리소스는 응답 목록에서 자동으로 제외할 수 있다.

**사용 사례**: 로드밸런싱(별도의 로드밸런서 없이 DNS 차원에서 단순하게 분산하고 싶을 때, 소규모 서비스나 비용 절감에 적합), 간단한 Failover(여러 IP 중 하나에 장애가 발생해도 나머지 정상 IP로 연결)

**장점**: 설정이 간단하다. 추가 비용이 거의 들지 않는다. Health Check와 연동하면 장애 리소스를 자동으로 제외할 수 있다.

**한계**: DNS 캐싱 때문에 실제 장애 전환 속도가 느려질 수 있다. 부하 분산이 정교하지 않다(클라이언트가 IP를 선택하는 방식에 따라 분산이 불균형해질 수 있다). 가중치나 지연 시간 기반 같은 고급 트래픽 관리 기능은 지원하지 않는다.

**정리**: Multivalue Answer Routing은 별도 로드밸런서 없이 "DNS 레벨의 단순 분산 + 최소한의 Failover"를 저비용으로 구현하고 싶을 때 적합한 정책이며, 정교한 트래픽 제어가 필요하다면 Weighted나 Latency-Based Routing을 검토해야 한다.

## 14. Weighted Routing Policy

여러 리소스를 하나의 도메인에 묶고, 각 리소스에 가중치(Weight)를 부여해서 트래픽을 비율대로 분배하는 정책이다.

**동작 방식**: 같은 이름과 타입의 레코드를 여러 개 만들고, 각각 다른 Weight 값을 지정한다. Weight가 높을수록 더 많은 요청이 분배된다. Weight 값의 범위는 **1~255**이다. 예를 들어 서버 A에 Weight 70, 서버 B에 Weight 30을 지정하면 전체 요청의 70%는 A로, 30%는 B로 분배된다. Health Check와 연동해서 비정상 리소스를 자동으로 제외할 수도 있다.

**사용 사례**: 로드밸런싱(서버 성능·용량에 따라 가중치를 조정), A/B 테스트(기존 버전 Weight 90, 신규 버전 Weight 10), 카나리 릴리즈(점진적 배포), Active-Active Failover(여러 리소스를 함께 운영하면서 가중치로 장애 시에도 안정적으로 분배)

**장점**: 트래픽 비율을 정교하게 조정할 수 있다. 단계적 배포나 실험 기능에 유연하게 대응할 수 있다. Health Check와 함께 사용하면 고가용성까지 확보할 수 있다.

**주의사항**: Weight는 상대값이기 때문에 합이 100일 필요는 없다(예: Weight 2와 8을 지정해도 비율은 20:80으로 계산된다). DNS 캐싱의 영향으로 실제 분배 비율이 약간 불균형해질 수 있다. 글로벌 트래픽 분배보다는 특정 리소스 간의 비율 조정에 더 적합하다.

**정리**: Weighted Routing은 8가지 정책 중 트래픽 비율을 가장 세밀하게 제어할 수 있는 정책으로, A/B 테스트나 카나리 배포처럼 "일부 트래픽만 새 버전으로 보내보고 싶은" 상황에 특히 적합하다.

## 15. 8가지 라우팅 정책 비교

| 정책 | 자동/수동 | Health Check 필요 여부 | 주요 용도 |
|---|---|---|---|
| Simple | - | 불필요 | 단일 서버로 트래픽 연결 |
| Failover | 자동(장애 감지 후 전환) | **필수** | Active-Passive 장애 조치, 재해 복구 |
| Geolocation | 수동(관리자가 지역 매핑) | 선택 | 지역별 콘텐츠·언어 분리, 규제 대응 |
| Geoproximity | 자동(Bias로 조정) | 선택 | 위치+Bias 기반 트래픽 분산 |
| Latency-Based | 자동(실측 지연 시간 기준) | 선택(권장) | 가장 빠른 리전으로 라우팅 |
| IP-based | 수동(CIDR 매핑) | 선택 | ISP·기업망·보안 기반 세분화 |
| Multivalue Answer | 자동(다중 응답) | 선택 | 저비용 DNS 레벨 부하 분산·간이 Failover |
| Weighted | 수동(Weight 지정) | 선택 | 비율 기반 로드밸런싱, A/B 테스트, 카나리 배포 |

**정리**: Failover만 Health Check가 사실상 필수이며, 나머지 정책들은 Health Check를 선택적으로 결합해 신뢰성을 높이는 구조다. "자동/수동" 구분은 리전·비율을 관리자가 직접 지정하는지, Route 53이 실측값으로 알아서 판단하는지의 차이로 이해하면 된다.

## 16. Health Check·라우팅 정책 설계 시 자주 놓치는 실무 포인트

| 흔한 실수 | 원인 | 방지 방법 |
|---|---|---|
| 18% 규칙을 모르고 있다가 예상 밖의 Unhealthy 판정을 받음 | 정상 응답 비율이 18%를 초과해야 Healthy로 간주된다는 규칙을 인지하지 못함 | Health Checker 대수와 리전 분포를 미리 확인하고, 일부 리전 장애만으로 전체가 Unhealthy로 판정될 수 있다는 점을 설계에 반영한다 |
| Failover 레코드를 만들면서 Health Check 연결을 빠뜨림 | Failover는 Health Check 없이도 레코드 생성 자체는 가능하다는 점을 오해 | Primary 레코드 생성 시 반드시 Health Check를 지정하고, 실제 장애 상황을 시뮬레이션해서 전환이 동작하는지 검증한다 |
| Geolocation Routing에 Default 라우팅을 만들지 않아 미지정 지역 접근 불가 | 설정한 지역 외 요청에 대한 기본 응답을 별도로 만들어야 한다는 점을 간과 | Geolocation 레코드를 구성할 때 반드시 Default(전 세계) 레코드를 함께 생성한다 |
| Health Checker의 `us-east-1` 리전 제한을 착각 | Health Checker 관리 리전과 점검 대상 리소스의 리전을 혼동 | Health Checker 자체는 `us-east-1`에서만 관리되지만, 점검 대상 리소스는 어떤 리전에 있어도 무방하다는 점을 구분해서 이해한다 |
| Weighted Routing에서 Weight 합을 100으로 맞추려고 함 | Weight가 절대 비율이 아니라 상대 비율이라는 점을 오해 | Weight는 상대값이므로 합계가 100이 아니어도 되며, 비율만 원하는 대로 나오면 된다는 점을 확인한다 |

**정리**: Route 53의 Health Check와 라우팅 정책에서 발생하는 실무 실수는 대부분 "숫자 규칙(18%, Weight 범위)을 정확히 모르는 경우"와 "필수 부가 설정(Health Check 연결, Default 라우팅)을 빠뜨리는 경우"로 요약된다. 각 정책의 특성과 규칙을 정확히 이해해 두면 대부분 사전에 방지할 수 있다.
