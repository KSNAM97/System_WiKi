## 1. Amazon Route 53 개요

**Amazon Route 53**은 AWS에서 제공하는 **DNS(Domain Name System)** 서비스이다. 서비스 이름은 DNS가 사용하는 기본 포트 번호인 53번에서 유래했다. DNS는 사람이 외우기 쉬운 도메인 이름(`www.example.com`)을 실제 서버가 사용하는 IP 주소로 바꿔주는 역할을 하며, Route 53은 이 변환 규칙을 관리하고 트래픽을 원하는 대상으로 전달하는 AWS의 관리형 DNS 서비스이다.

**주요 특징**

- **글로벌 서비스**: 단일 리전에 종속되지 않고 전 세계에 분산된 인프라를 기반으로 동작하며, 99.99% SLA를 통해 빠른 응답과 높은 안정성을 보장한다.
- **AWS 리소스와의 연동**: EC2, S3, ALB 같은 AWS 리소스를 간단히 도메인에 연결할 수 있으며, AWS 바깥에서 구입한 외부 도메인도 Route 53으로 가져와 관리할 수 있다.

**주요 기능**

- **도메인 관리**: 도메인 등록·갱신, A/CNAME/MX/TXT 같은 레코드 설정을 통한 리소스 연결
- **Health Check**: 지정한 서버·엔드포인트가 정상적으로 응답하는지 주기적으로 확인하고, 문제가 발생하면 자동으로 다른 리소스로 트래픽을 돌릴 수 있다.
- **라우팅 정책**: 단순 라우팅, 지리적 라우팅, 가중치 라우팅, 지연 시간 라우팅 등 트래픽을 어떻게 분산할지 정책 단위로 선택 가능 (자세한 내용은 [8. 라우팅 정책](#8-라우팅-정책) 참고)
- **하이브리드 아키텍처 지원**: 온프레미스 환경과 AWS 클라우드를 함께 쓰는 구성에서도 DNS 계층으로 활용할 수 있다.

**정리**: Route 53은 도메인 이름을 실제 리소스로 연결하는 DNS 서비스이면서, 동시에 Health Check와 라우팅 정책을 통해 트래픽을 제어하는 트래픽 관리 도구이기도 하다.

## 2. 비용 구조

| 비용 항목 | 설명 |
|---|---|
| 호스팅 영역(Hosted Zone) | 도메인 하나를 관리하기 위한 영역을 생성하면 월 0.50달러가 과금된다. |
| DNS 쿼리 | 사용자가 도메인을 조회할 때마다 요청 단위로 과금된다. |
| 부가 기능 | Health Check, 트래픽 관리 같은 추가 기능을 사용하면 별도 요금이 발생한다. |

**정리**: Route 53의 비용은 Hosted Zone을 유지하는 고정 비용과, 실제 조회량에 비례하는 쿼리 비용, 그리고 Health Check 같은 부가 기능 비용으로 나뉜다. Hosted Zone은 만들어두기만 해도 매달 청구되므로, 사용하지 않는 Hosted Zone은 반드시 삭제해야 불필요한 비용을 막을 수 있다.

## 3. 도메인과 서브도메인

**도메인(Domain)**은 사람이 읽기 쉬운 문자 주소로, 실제로는 서버의 IP 주소와 매핑되어 있다.

- **APEX 도메인(Zone Apex, Root Domain)**: 앞에 아무 문자열도 붙지 않은 가장 상위 단계의 순수한 도메인이다 (예: `example.com`).
- **서브도메인(Subdomain)**: APEX 도메인 앞에 문자열이 추가된 형태다 (예: `www.example.com`, `api.example.com`, `blog.example.com`).

**정리**: APEX 도메인은 도메인 소유권의 뿌리에 해당하며, 서브도메인은 그 뿌리 아래에서 용도별로 트래픽을 나누기 위한 구획이다. 이 둘의 구분은 뒤에서 다룰 CNAME과 Alias Record의 사용 가능 여부를 가르는 핵심 기준이 된다.

## 4. 레코드(Record)와 TTL

**레코드(DNS Record)**는 도메인이 어떤 방식으로 트래픽을 특정 대상에 전달할지 정의하는 데이터다. 어떤 도메인을 어떤 IP나 리소스로 연결할지, 메일은 어디로 보낼지, 소유권은 어떻게 검증할지 등을 레코드 단위로 지정한다. 구체적인 종류는 [6. 레코드 종류 상세](#6-레코드-종류-상세)에서 다룬다.

**TTL(Time To Live)**은 하나의 레코드가 다른 DNS 서버(리졸버)에 캐싱되어 유지되는 시간이다.

- TTL 값이 높으면 캐시가 오래 유지되어 DNS 쿼리 수가 줄어들지만, 레코드를 변경했을 때 반영이 늦어진다.
- TTL 값이 낮으면 변경 사항이 빠르게 반영되지만, 캐시가 자주 만료되어 DNS 쿼리 수와 비용이 늘어난다.

**정리**: TTL은 "쿼리 비용 절감"과 "변경 반영 속도" 사이의 트레이드오프를 조절하는 값이다. 평소에는 TTL을 여유 있게 잡아 비용을 아끼되, 장애 대응이나 마이그레이션처럼 빠른 트래픽 전환이 필요한 시점을 앞두고는 TTL을 미리 낮춰두는 것이 실무에서 흔한 패턴이다.

## 5. Hosted Zone

**Hosted Zone**은 특정 도메인 및 그 서브도메인들의 레코드를 모아서 관리하는 컨테이너다.

- APEX 도메인과 동일한 이름으로 생성된다.
- 하나의 도메인에 대해 하나의 Hosted Zone을 만들고, 그 안에 A, CNAME, MX 등 여러 레코드를 추가해서 관리하는 구조다.

**정리**: 도메인은 사람이 이해할 수 있는 주소이고, 레코드는 그 도메인을 실제 IP·리소스와 연결하는 규칙이며, TTL은 그 규칙이 갱신·반영되는 속도를 조절하는 값이다. Hosted Zone은 이 모든 레코드를 한데 묶어 관리하는 단위라고 정리할 수 있다.

## 6. 레코드 종류 상세

| 레코드 | 연결 대상 | Route 53 전용 | 설명 |
|---|---|---|---|
| **A (Address)** | IPv4 주소 | 아니오 | 가장 기본적인 레코드. 예: `example.com → 192.33.11.2` |
| **AAAA (IPv6 Address)** | IPv6 주소 | 아니오 | 차세대 주소 체계인 IPv6 환경에서 사용 |
| **CNAME (Canonical Name)** | 다른 도메인 이름 | 아니오 | 예: `www.example.com → example.com`. APEX 도메인에는 사용 불가 |
| **Alias Record** | AWS 리소스(S3, CloudFront, ALB 등) | 예 | Route 53 전용 확장 레코드. APEX 도메인에도 사용 가능, 추가 비용 없음 |
| **NS (Name Server)** | 권한 있는 DNS 서버 | 아니오 | 도메인을 실제로 관리하는 DNS 서버(Authoritative DNS)를 지정 |
| **MX (Mail Exchange)** | 메일 서버 주소 | 아니오 | 이메일 송수신을 위해 도메인과 메일 서버를 연결 |
| **TXT (Text)** | 텍스트 정보 | 아니오 | 도메인 소유권 검증, SPF/DKIM/DMARC 같은 이메일 보안 정책 저장 |

각 레코드의 역할을 조금 더 풀어보면 다음과 같다.

- **A / AAAA**: 도메인을 각각 IPv4, IPv6 주소에 직접 매핑하는 가장 기본적인 방식이다.
- **CNAME**: 도메인을 IP가 아니라 다른 도메인 이름으로 연결한다. `www`, `api`, `mail` 같은 서브도메인을 다른 도메인에 매핑할 때 주로 쓰이지만, APEX 도메인에는 DNS 표준 규칙상 사용할 수 없다.
- **Alias Record**: AWS Route 53에서만 지원하는 특별한 레코드 타입으로, 도메인을 S3·CloudFront·ALB 같은 AWS 리소스에 직접 연결한다. APEX 도메인에도 쓸 수 있고, 쿼리 비용 외의 추가 비용이 없으며, HTTPS 연결을 더 효율적으로 처리한다. 자세한 이유는 [7. Alias Record를 우선 사용하는 이유](#7-alias-record를-우선-사용하는-이유)에서 다룬다.
- **NS**: 도메인의 네임서버를 지정하는 레코드다. 외부 업체에서 구입한 도메인을 Route 53으로 위임하려면, 외부 등록 기관 쪽에 Route 53이 발급한 NS 레코드를 등록해야 정상 동작한다.
- **MX**: 이메일이 어느 메일 서버로 전달되어야 하는지 지정한다. 이메일을 주고받으려면 반드시 필요한 레코드다.
- **TXT**: 사람이 읽을 수 있는 임의의 텍스트를 저장한다. Google·AWS·Microsoft 같은 외부 서비스에 도메인 소유권을 증명하거나, SPF/DKIM/DMARC 같은 이메일 보안 정책을 설정할 때 사용한다.

**정리**: A/AAAA/CNAME/NS/MX/TXT는 DNS 표준에 정의된 범용 레코드이고, Alias Record만 Route 53이 AWS 리소스 연동을 위해 추가로 제공하는 확장 기능이다. 이 구분을 알아두면 "왜 APEX 도메인에는 CNAME을 못 쓰는데 Alias는 되는지"를 이해하는 기준이 된다.

## 7. Alias Record를 우선 사용하는 이유

AWS 리소스와 도메인을 연결할 때는 CNAME보다 Alias Record를 우선적으로 고려하는 것이 일반적이다. 이유는 크게 네 가지다.

**1) APEX 도메인 연결이 가능하다**

DNS 표준 규칙상 APEX 도메인에는 CNAME 레코드를 설정할 수 없다. APEX 도메인에는 이미 NS, SOA 같은 필수 DNS 정보가 들어 있기 때문이다. 예를 들어 `example.com`(APEX 도메인)을 ALB에 연결하려는 경우 CNAME으로는 불가능하지만, Alias Record를 사용하면 `example.com → ALB` 형태로 직접 연결할 수 있다. 따라서 ALB, CloudFront, S3 정적 웹 호스팅처럼 AWS 서비스를 루트 도메인에 직접 연결하려는 경우 Alias Record가 사실상 필수다.

**2) 비용이 발생하지 않는다**

일반 DNS 레코드(A, CNAME 등)는 조회(Query)가 발생할 때마다 비용이 과금되고, 트래픽이 많아질수록 비용도 늘어난다. 반면 Alias Record는 AWS 내부 리소스와 직접 연결되는 방식이라 별도의 DNS 쿼리 비용이 부과되지 않는다. 도메인 조회 비용이 절감되므로 대규모 서비스일수록 유리하다.

**3) HTTPS 연결을 더 효율적으로 처리한다**

일반 A/AAAA 레코드 방식에서는 클라이언트가 서버에 처음 접속할 때 서버가 HTTPS를 지원하는지 바로 알 수 없다. HTTP로 먼저 접속한 뒤 HTTPS 지원 여부를 확인하고 다시 HTTPS로 재연결하는 과정을 거치면서 연결 지연이 발생할 수 있다. 반면 Alias Record로 ALB·CloudFront 같은 AWS 리소스에 연결하면 HTTPS 지원 여부와 인증서 정보를 미리 알고 있으므로 첫 요청부터 바로 HTTPS로 연결할 수 있어 접속 속도와 사용자 경험이 개선된다.

**4) AWS 서비스와 자동으로 연동된다**

Alias Record는 AWS 전용 기능이라, 연결 대상이 바뀌어도 DNS 설정을 다시 수정할 필요가 없다. ALB가 재생성되거나 CloudFront가 재배포되어도 Alias는 자동으로 대상 정보를 추적한다. 반면 CNAME이나 A 레코드는 대상의 IP나 도메인이 바뀌면 직접 수정해야 한다.

**Alias vs CNAME 비교**

| 구분 | CNAME | Alias Record |
|---|---|---|
| APEX 도메인 사용 | 불가능 | 가능 |
| 비용 | 쿼리 수에 따라 과금 | 별도 쿼리 비용 없음 |
| HTTPS 처리 | 첫 접속 시 HTTP → HTTPS 재연결 과정 발생 가능 | 첫 요청부터 HTTPS로 바로 연결 |
| 대상 변경 시 | 직접 수정 필요 | 자동으로 추적 |
| 지원 범위 | DNS 표준 레코드 (모든 DNS 서비스에서 사용 가능) | Route 53 전용 |

**정리**: Alias Record는 CNAME이 가진 "APEX 도메인 사용 불가"라는 제약을 없애면서, 비용·HTTPS 처리·유지보수 측면에서도 이점이 있는 Route 53 전용 확장 기능이다. AWS 리소스를 도메인에 연결할 때는 CNAME보다 Alias Record를 우선 고려하는 것이 합리적이다.

## 8. 라우팅 정책

Route 53은 하나의 도메인에 대해 트래픽을 어떻게 분산할지 여러 라우팅 정책 중에서 선택할 수 있다.

| 정책 | 설명 |
|---|---|
| **단순 라우팅(Simple Routing)** | 가장 기본적인 정책으로, 하나의 도메인을 하나(또는 여러 개)의 리소스에 그대로 연결한다. |
| **지리적 라우팅(Geolocation Routing)** | 요청을 보낸 사용자의 위치에 따라 지리적으로 가까운 리소스로 트래픽을 전달한다. |
| **가중치 라우팅(Weighted Routing)** | 여러 리소스에 지정한 비율만큼 트래픽을 나누어 분산한다. |
| **지연 시간 라우팅(Latency-based Routing)** | 사용자에게 가장 빠른 응답 속도를 제공하는 리소스로 연결한다. |

**정리**: 이 문서에서 다루는 실습([AWS-G12-HA-Web-Service-Practice.md](g12-ha-web-service-practice.md))에서는 ALB 하나에 도메인을 연결하는 가장 단순한 라우팅 정책만 사용한다. 지리적·가중치·지연 시간 라우팅은 여러 리전이나 여러 환경(Blue/Green 배포 등)에 걸쳐 트래픽을 정교하게 분산해야 할 때 활용하는 정책으로, 여기서는 개념만 소개한다.

## 9. Route 53 사용 과정 3단계

**1) 도메인 등록**

도메인은 Route 53에서 직접 구입하거나, 외부 도메인 등록 기관(Domain Registrar)에서 구입할 수 있다. 단, `.kr` 같은 일부 국가 도메인은 Route 53에서 직접 구매가 불가능하다. 이미 도메인을 가지고 있다면 Route 53으로 가져와서 관리할 수도 있다.

**2) Hosting Zone 생성**

Route 53에서 도메인을 직접 등록한 경우에는 Hosting Zone이 자동으로 생성된다. 반대로 외부에서 도메인을 구입한 경우에는 Route 53에서 수동으로 Hosting Zone을 만든 뒤, 외부 도메인 관리 페이지에서 NS 레코드를 Route 53이 제공하는 네임서버 값으로 변경해야 한다. Hosting Zone은 해당 도메인의 DNS 레코드를 관리하는 컨테이너 역할을 한다.

**3) 레코드 생성**

AWS 리소스(S3 정적 웹사이트, CloudFront 배포, ALB 등)를 도메인과 연결할 때는 Alias Record를 사용한다. CNAME과 비슷한 역할을 하지만 APEX 도메인에도 적용할 수 있고, AWS 전용 기능이며 별도 비용이 들지 않는다.

**DNS 전파 시간**: 레코드를 변경해도 전 세계 DNS 서버에 반영되기까지 시간이 걸린다. 일반적으로 몇 분에서 몇 시간 내에 반영되지만, TTL 값에 따라 최대 하루(24시간) 이상 걸릴 수도 있다.

**정리**: Route 53을 사용하는 흐름은 "도메인 등록 → Hosting Zone 생성 → 레코드 생성"의 3단계로 요약된다. 각 단계에서 도메인을 어디서 샀는지(Route 53 vs 외부), 어떤 레코드 타입을 쓸지(CNAME vs Alias)가 갈리는 지점이 핵심이다.

## 10. 도메인 등록: Route 53 vs 외부 등록

**Part 1 — Route 53에서 직접 도메인 구입**

AWS Route 53 콘솔에서 원하는 도메인을 검색하고 바로 등록할 수 있다. 등록된 도메인은 Route 53에서 곧바로 관리할 수 있도록 설정되며, 이후 필요한 레코드(A, CNAME, MX 등)를 생성해 EC2·S3·ALB 같은 AWS 리소스와 연결하면 된다.

**Part 2 — 외부에서 구입한 도메인 연결**

이미 가비아, 카페24, GoDaddy 같은 다른 업체에서 구입한 도메인이 있다면, 해당 도메인의 네임서버(NS)를 Route 53에서 생성한 Hosted Zone의 네임서버로 변경해야 한다. 특히 `.kr` 같은 일부 도메인은 Route 53에서 직접 구입할 수 없으므로, 반드시 외부에서 구입한 뒤 Route 53으로 위임하는 방식을 써야 한다.

**비용 구조**

| 항목 | 설명 |
|---|---|
| 도메인 구입 비용 | Route 53에서 등록하면 연 단위로 과금된다 (예: `.com` 약 $12/년 수준). Route 53과 외부 등록 기관 어느 쪽에서 사더라도 도메인 등록 자체에는 별도 비용이 발생하며 프리 티어가 없다. |
| Hosted Zone 비용 | Route 53에서 Hosted Zone을 만들면 매달 $0.50이 과금되고, 여기에 DNS 조회 횟수에 따른 요금이 추가된다. 프리 티어가 없다. |

**정리**: 도메인을 어디서 사느냐(Route 53 직접 구입 vs 외부 등록 후 NS 위임)와 무관하게, Route 53으로 도메인을 관리하려면 Hosted Zone 비용은 반드시 발생한다는 점을 기억해야 한다.

## 11. Route 53 설계 시 자주 놓치는 실무 포인트

| 흔한 실수 | 원인 | 방지 방법 |
|---|---|---|
| APEX 도메인에 CNAME을 쓰려다 실패 | DNS 표준상 APEX 도메인에는 NS·SOA 정보가 이미 있어 CNAME을 추가로 설정할 수 없음 | APEX 도메인을 AWS 리소스에 연결할 때는 CNAME 대신 Alias Record를 사용한다 |
| TTL을 너무 높게 잡아 장애 시 트래픽 전환이 늦어짐 | TTL이 길수록 리졸버 캐시가 오래 유지되어 변경된 레코드가 늦게 반영됨 | 장애 대응·마이그레이션처럼 빠른 전환이 필요한 시점을 앞두고는 TTL을 미리 낮춰둔다 |
| `.kr` 같은 도메인을 Route 53에서 바로 사려다 실패 | 일부 국가 도메인은 Route 53에서 직접 구매를 지원하지 않음 | 외부 등록 기관에서 먼저 구입한 뒤, NS 레코드를 Route 53의 네임서버로 위임한다 |
| Hosted Zone을 삭제하지 않아 비용이 계속 청구됨 | Hosted Zone은 사용 여부와 무관하게 월 $0.50이 고정 과금됨 | 더 이상 쓰지 않는 도메인의 Hosted Zone은 확인 후 반드시 삭제한다 |

**정리**: Route 53에서 발생하는 실무 실수는 대부분 "DNS 표준 규칙(CNAME 제약)을 놓치는 경우"와 "비용이 계속 청구되는 리소스를 방치하는 경우" 두 가지로 요약된다. Alias Record의 특성과 Hosted Zone의 과금 구조를 정확히 이해해두면 대부분 예방할 수 있다.
