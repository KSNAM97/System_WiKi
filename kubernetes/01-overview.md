## 가상머신 vs 도커 컨테이너

| 구분 | 가상머신 (VM) | 도커 컨테이너 |
|------|------------|------------|
| OS | Guest OS 별도 설치 | Host OS 커널 공유 |
| 크기 | 무거움 (GB 단위) | 가벼움 (MB 단위) |
| 실행 속도 | 느림 | 빠름 |
| 비유 | 집을 통째로 만드는 방식 | 필요한 방만 가볍게 만드는 방식 |

### 가상머신 구조 (5단계)
```
Physical Infrastructure  ← 실제 서버 하드웨어
Host OS                  ← 물리 서버 운영체제
Hypervisor               ← 가상머신 생성·관리 소프트웨어
Guest OS                 ← 가상머신마다 별도 설치되는 OS
Bins & Libs + App        ← 실행 애플리케이션
```

### 도커 컨테이너 구조 (3단계)
```
Physical Infrastructure  ← 실제 서버 하드웨어
Host OS                  ← 물리 서버 운영체제 (커널 공유)
Docker Engine            ← 컨테이너 실행 엔진
Container 1, 2, 3...    ← App + 필요한 라이브러리만 포함
```

## 멀티호스트 도커 플랫폼

서버가 여러 대일 때 Docker 컨테이너를 분산하여 운영하는 구조다.

### 왜 필요한가

- 단일 서버는 CPU/RAM 용량 제한이 있어 컨테이너를 무제한 실행할 수 없다
- 서버 한 대 장애 시 전체 서비스 중단
- 웹, DB, 캐시 등을 하나의 서버에서 모두 운영하기 어려움

### 멀티호스트 구조 핵심

```
Node1 (192.168.1.2)  →  Container
Node2 (172.32.0.3)   →  Container    ← Overlay Network으로 연결
Node3 (10.0.1.5)     →  Container
```

**Overlay Network**: 서버 IP 대역이 서로 달라도 컨테이너끼리 동일한 내부 네트워크처럼 통신하게 해주는 기술

- 필요 포트: `2377/TCP`, `7946/TCP`, `7946/UDP`, `4789/UDP`

> **정리**: 멀티호스트 구조는 여러 대의 서버로 컨테이너를 분산시키지만, 자동 복구·오토 스케일링·통합 관리 기능이 없다는 한계가 있다.

### 멀티호스트 도커의 한계

| 문제 | 설명 |
|------|------|
| 자동 복구 불가 | 컨테이너 장애 시 수동 재시작 필요 |
| Auto Scaling 없음 | 트래픽 증가 시 수동으로 컨테이너 추가 |
| 복잡한 네트워크 관리 | Overlay·브리지·터널 등 직접 구성 |
| 배포 자동화 없음 | 롤링 업데이트, 롤백 기능 미제공 |
| 로드밸런싱 미지원 | 별도 설정·도구 필요 |
| 중앙 제어 없음 | 여러 서버를 통합 관리하는 시스템 부재 |

## 쿠버네티스 (Kubernetes / K8s)

멀티호스트 도커의 한계를 해결하기 위해 등장한 **컨테이너 오케스트레이션 시스템**이다.

- **K8s**: **Kubernetes**의 약칭 (`K` + 중간 8글자 + `s`)
- **의미**: 그리스어로 "조타수(배를 모는 사람)" — 컨테이너라는 배를 안전하게 관리하는 시스템

### 쿠버네티스가 해결하는 문제

| 문제 상황 | Docker만 사용할 때 | Kubernetes 사용 시 |
|---------|----------------|----------------|
| 서버 장애 | 컨테이너 전부 종료 | 다른 서버에서 자동 재실행 |
| 서버 배치 결정 | 수동으로 직접 지정 | 가장 적합한 서버에 자동 배치 |
| 서비스 업데이트 | 잠깐 다운타임 발생 | 무중단 롤링 업데이트 |
| 트래픽 급증 | 수동으로 컨테이너 추가 | 오토 스케일링 자동 처리 |
| 서버 간 네트워크 | 직접 설정 | 클러스터 네트워크 자동 구성 |

### 쿠버네티스의 주요 기능

| 기능 | 설명 |
|------|------|
| **컨테이너 자동 배포** | 여러 서버 중 어디에 올릴지 자동 결정 |
| **Self-Healing** | Pod 장애 시 즉시 자동 재생성 |
| **Auto Scaling** | 부하에 따라 컨테이너 수 자동 조정 |
| **Rolling Update** | 서비스 중단 없이 새 버전으로 배포 |
| **Service** | Pod 변경 시에도 고정 주소 접근 + 로드밸런싱 |
| **스토리지 관리** | 컨테이너 데이터 저장을 위한 볼륨 자동 관리 |

> **정리**: 쿠버네티스는 Self-Healing, Auto Scaling, Rolling Update, Service, 스토리지 관리 등을 통해 멀티호스트 도커의 한계를 자동화된 방식으로 해결한다.

## 컨테이너 오케스트레이션 기술 레이어

```
Layer 6 │ Development Workflow / Opinionated Containers │ OpenShift, Cloud Foundry
Layer 5 │ Orchestration / Scheduling / Service Model    │ Kubernetes, Docker Swarm
Layer 4 │ Container Engine                              │ Docker, Rocket, RunC, LXC
Layer 3 │ Operating System                              │ Ubuntu, RHEL, CoreOS
Layer 2 │ Virtual Infrastructure                        │ vSphere, EC2, GCP, Azure
Layer 1 │ Physical Infrastructure (실제 하드웨어)        │ Raw Computer, Network, Storage
```

쿠버네티스(Layer 5)는 컨테이너 엔진(Layer 4) 위에서 동작하며, 여러 서버의 컨테이너를 통합적으로 오케스트레이션한다.

> **정리**: 가상머신에서 컨테이너로, 다시 멀티호스트 도커에서 쿠버네티스로 이어지는 흐름은 결국 "여러 서버의 컨테이너를 어떻게 안정적으로 자동 관리할 것인가"라는 문제를 해결하는 과정이다.
